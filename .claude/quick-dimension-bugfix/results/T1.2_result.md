## Findings

### 1) BUG-11 invariant, restated in implementation-ready terms
At `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:593-599`, the collector currently creates `OpeningReferenceInfo(familyReference, fallbackPoint ?? estimatedPoint, label, ...)`. That is the broken association: the `Reference` identity comes from `FamilyInstance.GetReferences(Left/Right)`, but the physical point/station comes from a different derivation path (`fallbackPoint` or bbox-estimated point).

Implementation invariant for the fix:
- For each named `Reference` returned by `FamilyInstance.GetReferences(FamilyInstanceReferenceType.Left/Right)`, derive that reference's physical wall-axis station from geometry owned by that same `Reference`.
- The pair `{ reference identity, projected station }` must be produced atomically from one reference-resolution path.
- The collector must never assign a station to a named reference by reusing the sibling point, a bbox extremum, or any other point that was not derived from that same named reference.
- The forbidden shortcut is: infer physical order/station from the semantic label `"Left"` / `"Right"`.

This is exactly what shared contract R3 requires, expressed at the concrete fix site owned by T4.1/T4.2.

Conclusion from the documented API surface: `GetReferences(Left/Right)` gives a semantic/stable reference identity. The 2026 docs do not support the shortcut "Left label implies lower wall-axis station" or "Right label implies higher wall-axis station".

Implementation consequence: the only documented way to defend the BUG-11 invariant is to start from one `Reference`, resolve geometry from that same `Reference`, then compute the wall-axis station from that resolved geometry. Any station path that begins somewhere else is not reference-atomic.

### 4) Explicit API uncertainty that must not be guessed away
The missing documented link is this: no reliable 2026 page found in this task proves that a `Reference` returned by `FamilyInstance.GetReferences(FamilyInstanceReferenceType.Left/Right)` will always resolve via `Element.GetGeometryObjectFromReference` to a usable `Face`, `Edge`, plane, or line from which an origin/normal/station can be read directly.

What is documented:
- `GetReferences` returns references for family reference planes/lines.
- `GetGeometryObjectFromReference` can resolve a reference to a `GeometryObject`, or return `null`.

What is not documented by the sources used here:
- that a named family-instance reference plane/line always resolves to geometry with directly readable world-space placement data suitable for stationing;
- a 2026 official API that directly says "convert a named family reference to its placed plane/line transform".

Therefore the downstream rule is:
- treat "same-reference geometry resolution for named family refs" as required behavior to prove, not as already-guaranteed API behavior;
- do not replace that missing proof with the label-based shortcut that caused BUG-11.

### 5) Downstream-safe restatement for T4.1/T4.2
For each opening side independently:
1. Obtain the exact named `Reference` from `GetReferences(Left)[0]` or `GetReferences(Right)[0]` with index selection unchanged.
2. Resolve physical evidence from that same `Reference` only.
3. Compute the projected wall-axis station from that same resolved geometry only.
4. Store the named `Reference` together with that computed station as one indivisible association.
5. If step 2 or 3 cannot be proven for a named reference, that is an API/implementation gap to handle explicitly; it is not permission to reuse `fallbackPoint`, `estimatedPoint`, or label order for that named reference.

## Decision
The BUG-11 fix invariant is now settled: `FamilyInstance.GetReferences(Left/Right)` provides semantic reference identity only, and the fix must compute each named reference's wall-axis station from geometry owned by that same reference, never from `"Left"` / `"Right"` label semantics or from a separately derived fallback/estimated point. The direct 2026 API path from a named family reference to usable geometry remains an explicit uncertainty that downstream implementation must prove rather than assume.
