## Findings

### 1. `NewDimension` attachment is driven by `candidate.Reference`, not by `candidate.ElementId`

`QuickDimensionChainCreationService.CreateChainDimension` builds the `ReferenceArray` only from `candidate.Reference`, then passes that `ReferenceArray` into Revit `NewDimension`:

```csharp
ReferenceArray references = new ReferenceArray();
foreach (QuickDimensionCandidate candidate in result.Candidates)
{
    references.Append(candidate.Reference);
}
...
Dimension? dimension = doc.Create.NewDimension(view, dimensionLine, references);
```

Citations:
- `ArcTool.Core/Services/QuickDimensionChainCreationService.cs:75-79`
- `ArcTool.Core/Services/QuickDimensionChainCreationService.cs:93`
- `ArcTool.Core/Models/QuickDimensionContract.cs:431-458`
- `ArcTool.Core/Models/QuickDimensionContract.cs:463-472`
- Revit API Docs 2026: `ItemFactoryBase.NewDimension(View, Line, ReferenceArray)` — https://www.revitapidocs.com/2026/454df2e4-5ccb-b00d-434b-f3e7fdb75e8e.htm

This is the core non-blocking proof: the attachment path consumes `ReferenceArray`, and this code populates that array from `candidate.Reference` only. `candidate.ElementId` is not consulted by `CreateChainDimension` for dimension attachment.

### 2. Fallback references come from host-wall geometry, not from the opening instance

`TryGetHostWallOpeningReferences` reads geometry from `hostWall`, collects opening-edge references from that wall geometry, and returns the selected left/right references plus points:

- host-wall geometry acquisition and edge scan: `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:726-744`
- selected fallback references returned from host-wall edges: `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:805-817`

When fallback is chosen, `AddOpeningReferenceInfo` records the reference as `HostWallOpeningGeometry` and carries the fallback point unchanged:

```csharp
if (fallbackEnabled && useFallbackReference && fallbackReference != null && fallbackPoint != null)
{
    referenceInfos.Add(new OpeningReferenceInfo(
        fallbackReference,
        fallbackPoint,
        label,
        QuickDimensionReferenceStrategy.HostWallOpeningGeometry));
    return;
}
```

Citations:
- `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:583-590`
- fallback-only branch when no family ref exists: `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:603-609`
- strategy enum lock: `ArcTool.Core/Models/QuickDimensionContract.cs:40-66`

This proves the fallback reference identity is host-wall-owned before candidate metadata is written.

### 3. BUG-10 is introduced at candidate metadata assignment, not at attachment

In the main wall-axis flow, the candidate constructor always receives:
- `elementId = instance.Id`
- `hostElementId = hostWall.Id`
- `reference = referenceInfo.Reference`
- `referenceStrategy = referenceInfo.ReferenceStrategy`

Citations:
- main wall-axis flow candidate creation: `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:316-320`
- same pattern in deprecated intersection path: `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:535-545`

Because `referenceInfo.ReferenceStrategy` may already be `HostWallOpeningGeometry` at that point, a fallback candidate can carry a host-wall-owned `Reference` while still declaring `ElementId = opening instance`. That is the BUG-10 divergence.

The audit/logger confirms this exact meaning. Its owner-equality check explicitly compares the committed live reference owner against the candidate's declared `ElementId`, and its inline comment states that this is what surfaces BUG-10:

- `ArcTool.Core/Services/QuickDimensionReadOnlyXmlLogService.cs:627-638`

So the defect is metadata/audit-layer divergence, not a `NewDimension` creation failure.

### 4. Allowed edit boundary for T5.1

| Area | Allowed in T5.1? | Why |
|---|---|---|
| Fallback candidate ownership metadata only | Yes | BUG-10 originates where fallback `Reference` is wrapped into `QuickDimensionCandidate` metadata; creation path ignores `candidate.ElementId`. |
| Fallback candidate `ElementId` meaning | Yes | May be normalized to the live reference owner for `HostWallOpeningGeometry` candidates. |
| `HostElementId` meaning | Keep current host-wall context | Current constructor already records `hostWall.Id`; this is useful host context and is not the bug. |
| Fallback pair selection (`TrySelectNearestOpeningEdgePair`) | No | Pair selection and validation are geometry/reference-selection behavior, not metadata. See `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:771-817`. |
| Geometry points / projected stations / fallback points | No | BUG-10 is not a geometry defect; changing points would widen scope into BUG-11 or collection behavior. |
| `QuickDimensionReferenceStrategy` values | No | Enum is already locked and `HostWallOpeningGeometry` already expresses the provenance needed. See `ArcTool.Core/Models/QuickDimensionContract.cs:40-66`. |
| `QuickDimensionChainCreationService` transaction or `NewDimension` logic | No | Reference-only read target; not a fix site. See `ArcTool.Core/Services/QuickDimensionChainCreationService.cs:75-93`. |

### 5. Guardrail for future dedupe/grouping keyed on owner metadata

Until T5.1 normalizes fallback ownership metadata, any dedupe/grouping keyed on `QuickDimensionCandidate.ElementId` as if it were always the live reference owner is unsafe for `HostWallOpeningGeometry` candidates.

Safe interpretation boundary:
- `QuickDimensionCandidate.Reference` = attachment identity actually handed to `NewDimension`
- `QuickDimensionCandidate.ElementId` = currently unreliable owner metadata for fallback candidates
- `QuickDimensionCandidate.HostElementId` = host-wall context, not proof of reference ownership

This matches the logger's current bug-surfacing logic at `ArcTool.Core/Services/QuickDimensionReadOnlyXmlLogService.cs:627-638`.

## Decision

BUG-10 is settled as a metadata-only defect owned by `ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs`: fallback references may be host-wall-owned while fallback candidates still declare `ElementId = opening instance`. `QuickDimensionChainCreationService.CreateChainDimension` attaches dimensions from `candidate.Reference` through `ReferenceArray`, so BUG-10 is non-blocking for `NewDimension`. T5.1 may change only fallback candidate ownership metadata semantics; it must not touch geometry, fallback pair selection, strategy enums, or chain-creation logic.
