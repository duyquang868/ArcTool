The shared contract states that `dotnet build` fails with `MSB4803: ResolveComReference is not supported on the .NET Core version of MSBuild` and says to use `vswhere` only if the Visual Studio path differs. Source: `.claude/quick-dimension-bugfix/01_SHARED_CONTRACT.md:159-166`.
- Microsoft Learn confirms the reason and remedy:
  - `MSB4803` message text: `The task 'value' is not supported on the .NET Core version of MSBuild. Please use the .NET Framework version of MSBuild.` Source: [MSB4803 diagnostic code - MSBuild](https://learn.microsoft.com/en-us/visualstudio/msbuild/errors/msb4803?view=visualstudio).
  - `ResolveCOMReference` docs state: `This task is not supported on the .NET Core version of MSBuild, which is what's used when you run the dotnet build command from the command line. Try building the project by invoking MSBuild.exe ... since this executable uses the .NET Framework version of MSBuild.` Source: [ResolveComReference Task - MSBuild](https://learn.microsoft.com/en-us/visualstudio/msbuild/resolvecomreference-task?view=visualstudio).
- Runtime boundary is explicit and non-negotiable: no worker may launch Revit, open an `.rvt`, call any Revit MCP tool, click a ribbon command, or run a smoke test. Runtime proof stops at a written operator runbook; the human runs it and returns evidence. Source: `.claude/quick-dimension-bugfix/01_SHARED_CONTRACT.md:27-31`.
- Evidence must flow back through the operator queue, not direct runtime by workers. The queue template requires the master to ask for a named runbook, exact run instructions, and specific returned artifacts. Source: `.claude/quick-dimension-bugfix/04_EVIDENCE_QUEUE.md:5-29`.
- Exact evidence artifacts required from the operator per smoke run are:
  1. combined XML path(s) — one per run, with audit appended to the read-only XML;
  2. created dimension id(s);
  3. annotated screenshot(s) of displayed segment values;
  4. transaction/commit or rollback observation;
  5. optional journal excerpt.
  Source: `.claude/quick-dimension-bugfix/04_EVIDENCE_QUEUE.md:21-26`.
- Task T1.5 pass criteria are satisfied because both boundaries are now explicit: build verification path is unambiguous, and runtime ownership remains with the operator. Source: `.claude/quick-dimension-bugfix/tasks/T1.5_confirm_build_runtime_constraints.md:14-25`.
