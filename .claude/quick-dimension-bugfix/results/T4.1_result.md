## Findings

### 1. The collector already has the right carrier DTOs; the defect is the fill rule, not the downstream contract
The current BUG-11 site is still exactly the shared helper used by both collector paths:
- `TryProjectOpeningOntoWallAxis` builds `familyReferences`, `fallbackReferences`, then calls `AddOpeningReferenceInfo(...)` twice for Left/Right (`ArcTool.Core/Services/QuickDimensionDoorWindowCandidateCollector.cs:260-289`).
- `TryCollectOpeningCandidates` does the same in the deprecated intersection path (`...QuickDimensionDoorWindowCandidateCollector.cs:483-529`).
- `AddOpeningReferenceInfo` currently creates a `FamilyInstanceLeftRight` entry from `familyReference` plus `fallbackPoint ?? estimatedPoint` (`...QuickDimensionDoorWindowCandidateCollector.cs:624-662`).

That means the downstream pipeline is not the problem:
- `OpeningReferenceInfo` already carries `Reference`, `ReferencePoint`, `Label`, and `ReferenceStrategy` (`...QuickDimensionDoorWindowCandidateCollector.cs:1337-1354`).
- `OpeningReferencePair` already has `LeftReference`, `RightReference`, `LeftPoint`, and `RightPoint` slots (`...QuickDimensionDoorWindowCandidateCollector.cs:1279-1301`).

So the exact production change is: stop filling the named-reference branch with proxy points; start filling the existing point slots with reference-owned points.

### 2. Exact methods and DTOs that must change

| Symbol | Change required | Why |
|---|---|---|
| `TryGetFamilyInstanceReferences` | Keep `GetReferences(Left)[0]` / `GetReferences(Right)[0]` unchanged, but also resolve `LeftPoint` / `RightPoint` from the same named references' own geometry before returning the `OpeningReferencePair` | This is the narrowest place to bind named reference identity + physical point atomically |
| `AddOpeningReferenceInfo` | Replace `estimatedPoint` input with `familyPoint`; remove `familyReference + (fallbackPoint ?? estimatedPoint)` | This is the concrete BUG-11 edit |
| `TryProjectOpeningOntoWallAxis` | Stop treating bbox-estimated points as a prerequisite for named refs; pass `familyReferences.LeftPoint/RightPoint` into `AddOpeningReferenceInfo` | Named path must no longer depend on proxy geometry |
| `TryCollectOpeningCandidates` | Apply the same caller change as above | Shared helper must not preserve the old defect in the deprecated path |
| `DeriveProvenance` | Stop inferring named provenance from equality against fallback/estimated points; return `Reference-Owned (FamilyInstanceLeftRight)` for named path | Current logic would mislabel the fixed path as `Proxy-Derived (Unknown Source)` |
| `OpeningReferencePair` | No new fields required; its existing `LeftPoint` / `RightPoint` must now be populated for the family-reference path | Existing DTO is already sufficient |
| `OpeningReferenceInfo` | No structural change required; its existing `ReferencePoint` becomes the true reference-owned point for named refs | Downstream candidate creation already consumes the correct field |

`TryGetHostWallOpeningReferences` should remain behaviorally unchanged. It is still the owner of fallback-only `HostWallOpeningGeometry` references and proxy-derived host-wall edge points (`...QuickDimensionDoorWindowCandidateCollector.cs:743-872`).

### 3. Exact source edit plan for the named-reference branch

#### 3.1 Change `TryGetFamilyInstanceReferences` from “refs only” to “ref + owned point”
Keep the current selection logic exactly as-is:
- `instance.GetReferences(FamilyInstanceReferenceType.Left)` then `[0]`
- `instance.GetReferences(FamilyInstanceReferenceType.Right)` then `[0]`

That selection rule is preserved by contract and must not change (`01_SHARED_CONTRACT.md:38-39`). The 2026 API evidence supports this boundary:
- `FamilyInstance` exposes `GetReferences(FamilyInstanceReferenceType)` on the 2026 class page: [FamilyInstance Class](https://www.revitapidocs.com/2026/0d2231f8-91e6-794f-92ae-16aad8014b27.htm).

Inside the same method, after each `[0]` is chosen, resolve its physical point from that same reference's own geometry and store it into the returned `OpeningReferencePair.LeftPoint` / `.RightPoint`.

Recommended helper name inside the same file:
- `TryResolveReferenceOwnedPoint(FamilyInstance instance, Reference reference, XYZ? openingCenterPoint, out XYZ referencePoint)`

Recommended resolution order inside that helper:
1. Call `instance.GetGeometryObjectFromReference(reference)` on the **opening instance that owns the named reference**, not on the host wall. Autodesk 2026 documents this API on `Element`: [GetGeometryObjectFromReference](https://help.autodesk.com/cloudhelp/2026/ENU/Revit-API-MainReference/files/html/536b3d7a-ec8d-29f6-5957-751468c98dd0.htm).
2. If the resolved geometry is a `Face`, project the opening center point onto that face with `Face.Project(XYZ)` and use `IntersectionResult.XYZPoint` as the owned point. API citation: [Face.Project](https://www.revitapidocs.com/2026/4bee3e30-74fa-3103-c2f4-d07618fbcedf.htm).
3. If the resolved geometry is an `Edge`, reuse the file's existing linear-edge midpoint rule: call `Edge.AsCurve()`, require `Line`, and use the line midpoint. API citation: [Edge.AsCurve](https://www.revitapidocs.com/2026/4d780a44-c713-036f-840f-605527bbb2ce.htm). This matches the collector's current fallback edge handling in `CollectOpeningEdgeCandidates` (`...QuickDimensionDoorWindowCandidateCollector.cs:957-986`).
4. If the geometry is null or not stationable by those rules, return `false` and leave the family point null for that side.

This keeps the implementation inside the collector owner file and uses only documented 2026 APIs.

#### 3.2 Change `AddOpeningReferenceInfo` so the named path consumes `familyPoint`, never proxy points
Current bad branch (`...QuickDimensionDoorWindowCandidateCollector.cs:644-650`):
- `familyReference` + `fallbackPoint ?? estimatedPoint`

Required replacement logic:
1. Keep the existing validated fallback-first branch unchanged:
   - if `fallbackEnabled && useFallbackReference && fallbackReference != null && fallbackPoint != null`, emit `HostWallOpeningGeometry`.
2. Else, if `familyReference != null && familyPoint != null`, emit `FamilyInstanceLeftRight` using that `familyPoint`.
3. Else, if fallback is enabled and the collector is using fallback-only references, emit `HostWallOpeningGeometry` from `fallbackReference + fallbackPoint`.
4. Otherwise emit nothing for that side.

The key invariant is exact: **no code path may create `QuickDimensionReferenceStrategy.FamilyInstanceLeftRight` from `fallbackPoint`, `estimatedPoint`, bbox extrema, or any other proxy-derived point**.

That is the direct production translation of T3.3/T3.4 and the shared contract (`01_SHARED_CONTRACT.md:35-39`, `T3.3_result.md:31-40`, `T3.4_result.md:92-103`).

### 4. Caller changes required to make the named path truly independent of proxy geometry
Both caller methods currently front-load `TryGetEstimatedReferencePoints(...)` and abort early if it fails:
- wall-axis path: `...QuickDimensionDoorWindowCandidateCollector.cs:265-275`
- deprecated intersection path: `...QuickDimensionDoorWindowCandidateCollector.cs:488-503`

That guard exists only because the old named path needed proxy-derived points. After the fix, it becomes the wrong dependency.

Required caller change:
- `TryProjectOpeningOntoWallAxis` must no longer require `estimatedLeftPoint` / `estimatedRightPoint` before a named `FamilyInstanceLeftRight` candidate can be created.
- `TryCollectOpeningCandidates` must make the same change because it shares the same `AddOpeningReferenceInfo` helper.

Practical effect:
- compute `familyReferences = TryGetFamilyInstanceReferences(instance)` first;
- compute `fallbackReferences` exactly as today;
- pass `familyReferences.LeftPoint` / `.RightPoint` into `AddOpeningReferenceInfo`;
- remove `estimatedPoint` from the helper contract;
- do not abort the named path just because bbox estimation failed.

After this rewrite, `TryGetEstimatedReferencePoints` is no longer an approved input source for named references. If it becomes unused, it should be deleted in the same file as dead code created by the fix. That cleanup is in-scope because it is a direct consequence of removing the proxy pairing.

### 5. What proxy-derived path remains allowed
The allowed proxy-derived path is narrow and unchanged in ownership:
- `TryGetHostWallOpeningReferences` may still return host-wall opening-edge references plus `LeftPoint` / `RightPoint` midpoints (`...QuickDimensionDoorWindowCandidateCollector.cs:856-868`).
- Those points remain valid **only** for `QuickDimensionReferenceStrategy.HostWallOpeningGeometry` entries.
- They must never be injected into a `FamilyInstanceLeftRight` entry.

So the production rule becomes:
- named refs -> their own geometry-derived point -> `FamilyInstanceLeftRight`
- fallback refs -> host-wall edge midpoint -> `HostWallOpeningGeometry`
- never mix the two

This preserves the later BUG-10 edit boundary because BUG-10 is about fallback candidate metadata ownership, not fallback geometry or reference selection (`01_SHARED_CONTRACT.md:40-45`).

### 6. BUG-10 boundary preserved explicitly
This design does **not** touch any BUG-10-owned surface:
- no change to `TryGetHostWallOpeningReferences` pair-selection logic;
- no change to fallback `ReferenceStrategy` values;
- no change to `QuickDimensionCandidate` constructor arguments (`instance.Id`, `hostWall.Id`, `Reference`, `ReferenceStrategy`) in either caller (`...QuickDimensionDoorWindowCandidateCollector.cs:331-335`, `...QuickDimensionDoorWindowCandidateCollector.cs:586-596`);
- no change to wall anchors, mid-run logic, chain creation, dedupe, or audit semantics.

Specifically, the design does **not** retag fallback candidate `elementId` vs live-reference owner. That remains Phase 5 work exactly as requested.

### 7. Minimal provenance fix needed for operator evidence
`DeriveProvenance` currently proves named-path provenance by comparing `ReferencePoint` to `fallbackReferences.LeftPoint/RightPoint` and `estimatedLeftPoint/RightPoint` (`...QuickDimensionDoorWindowCandidateCollector.cs:362-390`). After the BUG-11 fix, that logic becomes stale.

The narrow correction is:
- `HostWallOpeningGeometry` -> `Reference-Owned (HostWallOpeningGeometry)`
- `FamilyInstanceLeftRight` -> `Reference-Owned (FamilyInstanceLeftRight)`

No new strategy enum is needed, and no changes are needed in `QuickDimensionContract.cs`. This keeps the post-fix XML evidence readable without widening scope.

## Decision
PASS. The exact production edit is to populate `OpeningReferencePair.LeftPoint/RightPoint` for the named family-reference path from the same `Reference`'s own geometry inside `TryGetFamilyInstanceReferences`, then rewrite `AddOpeningReferenceInfo` so `FamilyInstanceLeftRight` entries consume only those owned points and never `fallbackPoint ?? estimatedPoint`; `TryProjectOpeningOntoWallAxis` and `TryCollectOpeningCandidates` must drop bbox-estimation as a named-path prerequisite, while `TryGetHostWallOpeningReferences` and all BUG-10-owned metadata surfaces stay unchanged.
