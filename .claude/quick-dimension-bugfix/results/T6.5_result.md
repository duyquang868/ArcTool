## Findings

1. The reopen-persistence half can be stated precisely and safely.
   - The shared contract requires a post-reopen observation and makes “success survives close/reopen of the document” a mission gate (`01_SHARED_CONTRACT.md:152-155`, `01_SHARED_CONTRACT.md:170-179`).
   - EV-2 already requires each committed valid run to return the created dimension id, so reopen validation can target previously committed valid dimensions by id instead of asking the operator to rediscover them visually (`04_EVIDENCE_QUEUE.md:50-60`, `results/T6.1_result.md:34-55`).
   - Safe reopen check, stated exactly: after at least one valid EV-2 run has committed, save the model, close the document, reopen the same model, and confirm the previously recorded committed dimension id(s) still exist and display the same segment geometry as before reopen.

2. The rollback half cannot be stated precisely from operator inputs alone.
   - `QuickDimensionCreateChainSmokeCommand` rejects every known operator-controlled invalid input before `QuickDimensionChainCreationService` starts its creation transaction:
     - unsupported active view returns `Result.Cancelled` (`QuickDimensionCreateChainSmokeCommand.cs:37-45`);
     - invalid wall / curtain wall / non-line wall returns `Result.Cancelled` (`QuickDimensionCreateChainSmokeCommand.cs:49-76`, `249-277`);
     - side pick on the wall axis returns `Result.Cancelled` (`QuickDimensionCreateChainSmokeCommand.cs:81-99`);
     - read-only result with fewer than two distinct-station candidates returns `Result.Cancelled` before creation (`QuickDimensionCreateChainSmokeCommand.cs:107-116`; `QuickDimensionContract.cs:576-577`).
   - The actual creation transaction begins only inside `QuickDimensionChainCreationService.CreateChainDimension` at `QuickDimensionChainCreationService.cs:88-89`.
   - Internal rollback happens only after that point, and only when `doc.Create.NewDimension(...)` returns null, created reference count differs from expected candidate count, transaction commit status is not `Committed`, or an exception is thrown (`QuickDimensionChainCreationService.cs:93-149`, rollback helper `153-159`).
   - No package evidence identifies a reproducible wall/shell/operator action on the fixed build that deterministically triggers one of those post-start rollback branches. The fixed-build handoff in T5.5 is explicitly framed for valid regression runs and reopen evidence, not for a known forced-rollback fixture (`results/T5.5_result.md:10-23`, `33-38`).

3. Because of that control-flow split, the required “one intentional invalid-reference or expected-failure run that should rollback cleanly” is not request-ready.
   - A curved wall, curtain wall, unsupported view, or side pick on the axis would prove cancellation only, not rollback.
   - An “expected-failure” rollback fixture cannot be named safely because none is verified in the package inputs.
   - Claiming any specific wall/shell will roll back would be guesswork, which the shared contract forbids (`01_SHARED_CONTRACT.md:46-50`).

4. Revit API references consulted for transaction/close vocabulary:
   - `Transaction.RollBack()` reference page: https://www.revitapidocs.com/2026/bd1e69e9-961e-1c07-f70a-a29b90c6eb97.htm
   - `Document.Close(bool)` reference page: https://www.revitapidocs.com/2026/5948b03d-5537-33d4-6e38-a8f16d5d6779.htm
   - The blocking conclusion above is based on ArcTool source control flow, not on undocumented assumptions about Revit runtime behavior.

## Decision

BLOCKED. The reopen validation steps are precise, but the rollback-validation half is not: the current fixed build exposes only pre-transaction operator failures and post-start rollback branches that are not operator-directable from any verified fixture in this package, so EV-3 cannot be requested directly from a precise safe runbook yet.

## Open questions

1. Is there a known wall/shell on the fixed build that consistently reaches transaction start and rolls back? If yes, the master needs that verified fixture id and the operator observation.
2. If no such fixture exists, is the master willing to authorize a dedicated rollback harness or debug switch that intentionally injects a post-start invalid reference without changing the production fix surface?

## Handoff for downstream tasks

- Do not request EV-3 yet as a PASS runbook.
- The reopen-only portion is settled: use previously committed valid dimension id(s) from EV-2, then record one reopen persistence observation confirming those id(s) still exist after save/close/reopen.
- To unblock the full rollback + reopen request, the master needs either a reproducible rollback fixture from the operator or an explicitly authorized harness that can force a post-transaction-start failure safely.
