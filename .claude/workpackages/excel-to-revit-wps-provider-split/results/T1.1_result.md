### 4. COM release order rules to preserve

- Global rule: release child COM wrappers before their parent (`ExcelInteropService.cs:361-388`
  comment "Release theo thứ tự: workbook → app").
- `GetSheetNames` (402-430): release each `Worksheet` inside the loop immediately after reading
  `.Name` (416), then release the `Sheets` wrapper in `finally` (426) — child (`Worksheet`) before
  parent (`Sheets`).
- `GetNamedRanges` (443-494): release `Range r` right after the sheet-match check (469), release
  each `Name` in the loop's own `finally` (479), release the `Names` wrapper last in the outer
  `finally` (490) — three-level child→parent chain: `Range` → `Name` → `Names`.
- `ExportRegion` (512-582): release `targetRange` before `ws` in `finally` (579-580) — range is
  child of worksheet.
- `Dispose` (361-378): `_workbook.Close(false)` then `ReleaseObject(_workbook)`, then
  `_excelApp.Quit()` then `ReleaseObject(_excelApp)` — workbook released before application; no
  `ReleaseComObject` call follows any `Delete`-type operation anywhere in the read ranges (no
  `Delete` calls exist in this code), so that half of the rule has nothing to violate but must
  still be honored by new provider code.

## Decision

`ISpreadsheetPdfExporter` is confirmed as a disposable session covering open + enumerate +
export-to-PDF, matching the contract's correction that a single `ExportRegionToPdf` method cannot
carry the UI's sheet/region enumeration needs. Five points settled:

1. **`Open` returns `bool`, never throws.** Today's `OpenFile` (`ExcelInteropService.cs:32-48`)
   wraps everything in `try/catch` and returns `false` on any failure, including a bad path or a
   COM activation failure. The interface preserves that exact contract — the session swallows the
   exception internally and reports failure via the return value. `ExcelSyncEngine.cs:162-168`
   already does the throw-on-`false` translation at the call site (`InvalidOperationException`
   with a Vietnamese user-facing message); that translation logic stays in the caller/coordinator,
   not in the provider.
2. **The coordinator owns temp-PDF lifetime, not the provider.** Today `ExportRangeInternal`
   deletes its own temp PDF in a `finally` block once rendering is done (contract §4, "temp-PDF
   cleanup at 357 moves to the caller that owns the temp file"). After the split,
   `ExportRegionToPdf` writes the PDF to the caller-supplied `outputPdfPath` and returns; it must
   not delete that file. The coordinator (`SpreadsheetImageExportService`) is the one that creates
   the temp path, calls `ExportRegionToPdf`, hands the PDF to `PdfRasterImageService`, and deletes
   the temp PDF afterward.
3. **Region resolution (NamedRange → PrintArea → UsedRange) stays inside the provider.** Confirmed
   — it is pure COM work (`Worksheet.Range[...]`, `PageSetup.PrintArea`, `Worksheet.UsedRange`, all
   requiring a live COM `Worksheet`/`Workbook`), and `ExportRegion` (`ExcelInteropService.cs:512-582`)
   already implements exactly this fallback chain end to end. No engine-agnostic code touches COM
   objects, so this logic cannot move out of the provider without leaking COM types upward.
4. **`GetSheetNames`/`GetNamedRanges` keep swallow-and-return-empty behavior.** Confirmed — both
   methods today catch their own exceptions, log via `Debug.WriteLine`, and return an empty (but
   non-null) list rather than throwing (`ExcelInteropService.cs:419-422` for sheets,
   `483-486` for named ranges). `ExcelToRevitWindow.xaml.cs:428-443` and `:473-475` consume these
   lists directly to populate WPF dropdowns with no null-check or try/catch around the calls —
   changing this to throw would crash `LoadLookupData`/`LoadRegionOptionsForRow` on any workbook
   quirk. The interface signature `IReadOnlyList<string>` (never null, may be empty) preserves this.
5. **Keep `SpreadsheetEngine Engine { get; }` on the interface.** Decision: keep it. The coordinator
   needs to log/report which engine actually served a given export (useful for the WPS-fallback
   diagnostics and EV-1/EV-2/EV-3 evidence gathering per the contract's fixtures), and exposing it
   on the session is cheaper than the coordinator tracking a separate engine flag that must be kept
   in sync with which concrete provider it instantiated. A provider-agnostic caller (like
   `ExcelSyncEngine`) can ignore the property entirely; it costs nothing when unused.
