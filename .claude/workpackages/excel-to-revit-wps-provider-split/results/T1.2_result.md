## Findings

### 1. ProgID probe order and rationale

Chain, in order: `KET.Application` → `ET.Application` → `Kingsoft.ET.Application`. No further
candidates added. `KET.Application` is the only one confirmed to resolve (given fact); the other
two stay only because the user directed keeping them for other WPS builds — both remain
unverified everywhere. Rejected additions: `Kingsoft.ET` (no suffix) and `ET.Sheet.8` — no
citation found (both searches empty) and R3 forbids adding untested ProgIDs on guesswork; an
extra candidate that resolves to the wrong server is worse than a shorter chain that fails
cleanly (see `KWPS.Application` below). Per-user (HKCU) registration means detection code must
call `GetTypeFromProgID` per-process with no assumption of machine-wide visibility — no special
handling needed beyond using the standard API, since HKCU is transparent to `GetTypeFromProgID`
for the current user, but this means service/other-user contexts will see `null` even when WPS
is installed for the interactive user. Note as an operational caveat, not a code branch.

**Explicit denylist:** `KWPS.Application` must never be added to this chain even as a last
resort. It resolves and instantiates (it is Writer), so it would pass ProgID probing and produce
a live COM object with no spreadsheet members — worse than "engine absent" because failure moves
from clean type-resolution rejection to a deep `MissingMemberException` on the first
`Workbooks` access. Reject by ProgID name, not by member-probing after the fact.

Probe mechanism, exact sequence per candidate:
1. `Type t = Type.GetTypeFromProgID(progId, throwOnError: false);`
2. `if (t == null) continue;` — not registered, not an error, no exception path.
3. `try { instance = Activator.CreateInstance(t); } catch (COMException ex) { log "resolved but activation failed: {progId}: {ex.Message}"; continue; }` — a resolving-but-non-instantiable type (stale registration) is a real, reported failure mode; it does not abort the whole probe, it rolls to the next candidate.
4. Immediately smoke-test viability: attempt the two baseline `SetProperty` calls (Visible, DisplayAlerts — see table row 1-2). If either throws, treat identically to an instantiation failure (roll to next candidate); a COM object that rejects its two most basic property sets will not survive `Workbooks.Open`.
5. First candidate to pass steps 2-4 wins and becomes the session's live `Application` object.
6. If every candidate fails step 2 or 4 → provider construction fails → `EngineAbsent` (§4). Retain the last captured exception message (if any) for diagnostics — it distinguishes "nothing registered at all" from "something registered but broken," which matters for the `EV-1` runbook.

**Row 17 detail (most error-prone call, per task instruction).** `Range.Address(RowAbsolute,
ColumnAbsolute)` is a parameterized property, not a plain method. Model it exactly as a
`GetProperty` invocation carrying the index arguments:
`type.InvokeMember("Address", BindingFlags.GetProperty | BindingFlags.Public | BindingFlags.Instance, null, rangeObj, new object[] { false, false })`.
Fallback if that throws (`MissingMemberException` or an argument-binding `COMException`): retry
with no arguments — `InvokeMember("Address", BindingFlags.GetProperty, null, rangeObj, null)` —
which yields Excel's default absolute `$A$1`-style address; strip `$` before reuse as a
`PrintArea` string, or pass it through unchanged since `PrintArea`'s setter is documented as
tolerant of both forms. If both forms throw for every candidate range in the resolution chain
(NamedRange, PrintArea, UsedRange), that is fatal for `ExportRegionToPdf`. ASSUMPTION (untested,
for `EV-1`): whether WPS additionally needs `BindingFlags.GetProperty | BindingFlags.InvokeMethod`
combined to dispatch a parameterized property through `IDispatch` — this is generic late-binding
folklore, not sourced to a specific citable reference; `EV-1` must confirm the minimal flag
combination that actually succeeds against WPS's `IDispatch` implementation before `T3.2` locks
one shape in code.

**Row 25 detail.** Positional argument order/count must match today's code exactly:
`(Type, Filename, Quality, IncludeDocProperties, IgnorePrintAreas, From, To, OpenAfterPublish)`.
If it throws specifically on argument count/type binding (as opposed to the member not existing
at all), that is a distinct diagnostic worth capturing for `EV-1`, but the production path must
not silently guess a shorter signature — that guess is unauthorized without `EV-1` confirmation.

**Worksheet-scope `Names` — not needed.** T1.1 §2 shows only `Workbook.Names` (line 452) in the
current behavior; no worksheet-scope `Names` collection appears anywhere in the read ranges. Per
R2 (no scope widening), the WPS provider must not add a worksheet-scope `Names` lookup — the
task's "if applicable" qualifier resolves to "not applicable."

### 4. Failure semantics, mapped onto the T1.1 session shape

| Condition | When | Session-level effect | Coordinator-facing category |
|---|---|---|---|
| No ProgID resolves | provider construction (before any `Open`) | provider factory returns null / construction fails | `EngineAbsent` — same bucket as "no WPS installed" |
| Type resolves, instantiation throws | provider construction | same as above, rolls to next candidate (§1 step 3); last exception retained for logs | `EngineAbsent`, diagnostic message differs internally ("registered but broken" vs "not registered") |
| `Workbooks.Open` throws | after successful construction | `Open(path)` returns `false` (T1.1 pt.1 contract preserved — never throws) | `EngineFoundOpenFailed` — distinct from `EngineAbsent`; engine is live, this file/path failed |
| Sheet name not found | `ExportRegionToPdf(sheetName, ...)` after `Open` succeeded | that call returns `false`; `GetNamedRanges(sheetName)` instead returns empty list (T1.1 pt.4 swallow behavior, unchanged) | `EngineFoundExportFailed`, reason "sheet not found" |
| `ExportAsFixedFormat` missing | during `ExportRegionToPdf`, row 25 throws `MissingMemberException` | `ExportRegionToPdf` returns `false`; internal log captures the missing-member detail | `EngineFoundExportFailed`, reason "PDF export unsupported on this WPS build" — the headline case the task calls out; surfaced distinctly in logs even though the interface only returns `bool` |
| PDF file absent after call returns normally | after row 25 returns without throwing | provider must `File.Exists(tempPdfPath)` explicitly before reporting success; if absent, `ExportRegionToPdf` returns `false` | `EngineFoundExportFailed`, reason "no output produced" — **new check, no MS-provider precedent** (T1.1 §2 lists no such post-call check); justified because `wps.exe /prometheus /et /Automation` runs the spreadsheet as a shell mode rather than a dedicated server, so a silently-async or silently-failed write is a real risk the MS Excel COM behavior does not have to guard against |

The two categories the task asks the coordinator (`T3.3`) to distinguish are `EngineAbsent`
(nothing to fall back to — user message: "no spreadsheet engine found") vs `EngineFound*Failed`
(WPS is live, this specific operation failed — user message should name the operation, not claim
the engine is missing). Both `EngineFoundOpenFailed` and `EngineFoundExportFailed` still surface
through `bool`-returning methods per the locked interface; the category distinction lives in the
internal log line each failure path writes, not in a new return type — consistent with T1.1's
decision to keep `Open`/enumerate/export swallowing exceptions rather than throwing.

### 5. COM release discipline for late-bound objects

Same child→parent ordering as T1.1 §4, extended for late-binding's specific hazard: **every**
`InvokeMember` call that returns a COM object (not a primitive/string/bool/number) must be
captured into its own local variable before the next call is made on it. Chaining
(`Invoke(Invoke(Invoke(app,"Workbooks"),"Item",1),"Name")` in one expression) creates untracked
intermediate RCWs (`Workbooks` collection, the `Worksheet` item) with no variable to pass to
`Marshal.ReleaseComObject`; they then depend on GC finalization, which for COM objects can leave
the WPS host process alive after `Quit` — a stale-process leak that is invisible until someone
notices `wps.exe` never exits.

Rule: one `InvokeMember` call per statement when the result is a COM object; release in `finally`
in this order, mirroring T1.1 §4 exactly (no new release calls invented beyond what the reference
code does):
- `GetSheetNames`: release each `Worksheet` inside the loop right after reading `Name`, then
  release `Worksheets` last.
- `GetNamedRanges`: release `Range` right after the sheet-match check, release each `Name` in the
  loop's own `finally`, release `Names` last in the outer `finally` — three-level chain.
- `ExportRegionToPdf`: release `targetRange` before `worksheet` in `finally`. Note `pageSetup` is
  **not** separately released in the reference code's finally block (`ExcelInteropService.cs:
  188-230` shows no `ReleaseComObject(pageSetup)`) — the WPS provider must match that, not add a
  release the reference implementation doesn't have.
- `Workbooks` (the collection, not the `Workbook`): release immediately after `Open` returns; it
  is a short-lived intermediate with no other use, consistent with it not appearing anywhere in
  T1.1's persistent-object list.
- `Dispose`: `workbook.Close(false)` → release `workbook` → `app.Quit()` → release `app`,
  identical order to T1.1 §4 row 4.

## Decision

The WPS provider probes exactly `KET.Application` → `ET.Application` → `Kingsoft.ET.Application`
in that order, with `KWPS.Application` explicitly denylisted; construction failure at any stage
maps to `EngineAbsent`. All 27 `InvokeMember` call shapes are specified with target, member,
`BindingFlags`, argument array, and a fatal/tolerable classification that mirrors the MS
provider's own tolerances (`PaperSize` is the sole pre-existing tolerable property; the
post-export `File.Exists` check is the one new, WPS-specific tolerance, justified by the
shell-mode server risk). All four numeric constants are sourced for Excel and explicitly flagged
as unverified-for-WPS assumptions rather than claimed as verified WPS behavior. Release discipline
extends the T1.1 child→parent rule with a no-chaining rule specific to late binding's untracked-
intermediate hazard. Web search for WPS-specific citations produced nothing usable in this
session; every WPS behavioral claim above is either explicitly marked ASSUMPTION or classified in
the failure-semantics table for `EV-1`/`EV-2` to test — none is stated as verified.
