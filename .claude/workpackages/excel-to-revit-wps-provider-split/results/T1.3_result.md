## Findings

### Q1 — Interop leak: NO leak, GO

T1.1 §1 locks the interface as:
```csharp
public interface ISpreadsheetPdfExporter : IDisposable
{
    SpreadsheetEngine Engine { get; }
    bool Open(string filePath);
    IReadOnlyList<string> GetSheetNames();
    IReadOnlyList<string> GetNamedRanges(string sheetName);
    bool ExportRegionToPdf(string sheetName, string regionName, string outputPdfPath);
}
public enum SpreadsheetEngine { MsExcel, Wps }
```
Every parameter and return type is `string`, `bool`, `IReadOnlyList<string>`, the locally-defined
`SpreadsheetEngine` enum, or `IDisposable` (BCL). None of these require
`Microsoft.Office.Interop.Excel` or any `Xl*` enum to appear in `WpsWorkbookPdfExporter.cs`. T1.2's
27-row `InvokeMember` table (§2) keeps every live COM handle as an untyped `object` local
(late-bound), matching §5's no-chaining rule — nothing there forces an Interop type into scope
either. No design defect; no fix needed.

### Q5 — Missing-engine diagnostics: distinguishable, no interface change needed

T1.2 §4 defines three categories: `EngineAbsent` (no ProgID resolves, or resolves but
`Activator.CreateInstance` throws — both happen at **construction time**, before `Open` is ever
called), `EngineFoundOpenFailed` (`Open` returns `false` after successful construction), and
`EngineFoundExportFailed` (`ExportRegionToPdf` returns `false` after a successful `Open`).

The locked interface (T1.1 §1) has no diagnostic-category member — `Open`/`ExportRegionToPdf` are
plain `bool`. That is sufficient, not a gap: `EngineAbsent` is signaled at the *factory* layer
(provider construction fails → coordinator's per-engine probe returns null/throws-caught, coordinator
moves to the next engine or reports "no engine found"), while `EngineFound*Failed` is signaled by a
constructed, live provider returning `false` from `Open`/`ExportRegionToPdf`. The coordinator needs
only two signals it already has — "did any provider construct" and "did the constructed provider's
call return true" — to build the two user-facing message categories the task asks for. T1.2 §4's
closing paragraph states this explicitly: the category distinction "lives in the internal log line
each failure path writes, not in a new return type," which matches what T1.1 already locked.

Carry-forward note (non-blocking): neither T1.1 nor T1.2 specifies the exact factory method shape
(e.g. `static ISpreadsheetPdfExporter? TryCreate(string filePath)`) that lets the coordinator detect
construction failure without a source-file change to the interface. This is a `T3.1`/`T3.2`/`T3.3`
implementation-convention detail, not a design defect — nothing in the locked interface prevents a
static factory per provider class, and the manifest already assigns `T3.3` sole ownership of the
coordinator that would call it.

to Phase 5 evidence-gathering and does not block Phase 2-4 code authoring (Q6). Phase 2 may start.
