## Findings

1. Implemented the coordinator at `ArcTool.Core/Services/Excel/SpreadsheetImageExportService.cs` with the same surface shape the three existing call sites already use, so T3.5/T3.6 can be mechanical rewires.

```csharp
public class SpreadsheetImageExportService : IDisposable
{
    public SpreadsheetEngine? ActiveEngine => _provider?.Engine;
    public bool OpenFile(string filePath);
    public List<string> GetSheetNames();
    public List<string> GetNamedRanges(string sheetName);
    public bool ExportRegion(string sheetName, string regionName, string outputPngPath);
    public void Dispose();
}
```

2. Detection is contained in this file only and respects R10 exactly.
   - MS Excel is probed first via `Type.GetTypeFromProgID("Excel.Application", false) != null`.
   - WPS is probed only if MS Excel does not resolve, in this fallback order: `KET.Application`, `ET.Application`, `Kingsoft.ET.Application`.
   - Probing is registration-only and does not instantiate either engine, matching the task's preference to avoid launching an app as a side effect.
   - Detection is instance-local: no static cache, no process-wide memory that could outlive an install/uninstall mid-session.

3. The three required failure modes are now distinguishable enough for downstream caller diagnostics without widening `ISpreadsheetPdfExporter`.
   - No engine installed: `OpenFile` returns `false` and writes a diagnostic naming both Microsoft Excel and WPS Spreadsheet ProgIDs.
   - Engine present but workbook open failed: `OpenFile` returns `false` and writes a diagnostic naming the detected engine (`Microsoft Excel` or `WPS Spreadsheet (<ProgID>)`) plus the workbook path.
   - Engine present, workbook opened, export failed: `ExportRegion` returns `false` and writes a diagnostic naming the active engine plus sheet/region context.
   This preserves the observable contract at the existing callers: `ExcelSyncEngine.cs:162-178` still sees `OpenFile == false` vs `ExportRegion == false` as separate outcomes, and `ExcelToRevitWindow.xaml.cs:423-475` still uses the enumeration methods only after a successful open.

4. Temp-PDF ownership now lives in the coordinator exactly as the task required.
   - Path pattern implemented as `Path.Combine(Path.GetTempPath(), $"ArcTool_ExcelSync_{Guid.NewGuid():N}.pdf")`, matching the old naming pattern cited by the task.
   - Flow is coordinator-owned and ordered: provider `ExportRegionToPdf(...)` → `PdfRasterImageService.RenderPdfToCroppedPng(...)` → temp PDF delete in `finally`.
   - The `finally` delete is non-throwing: `File.Exists`/`File.Delete` are wrapped in a nested `try/catch`, so temp cleanup cannot mask a real export or raster failure.

5. Provider lifetime and dispose behavior are coordinator-safe.
   - `Dispose()` is idempotent via `_disposed` guard.
   - Underlying provider disposal is isolated in `DisposeProvider()` and swallows provider-dispose exceptions, then nulls `_provider`.
   - `OpenFile()` disposes any prior provider session before creating a new one, preventing multiple live sessions from one coordinator instance.

6. No forbidden scope widening was introduced.
   - No edits to `ArcTool.Core.csproj`, either provider, `ExcelInteropService.cs`, `ExcelSyncEngine.cs`, or `ExcelToRevitWindow.xaml.cs`.
   - No COM enum types, no `InvokeMember`, and no spreadsheet-automation logic beyond ProgID detection/provider selection appear in the coordinator.
