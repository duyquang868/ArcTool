## Findings

**Resolving the EV-1c/EV-1d vs EV-1e contradiction.** EV-1d (line 9, `EV-1d_root_cause_result.md`) reported `Application.Workbooks` returning `null` across three binders and a 10x retry loop. EV-1e (STAGE C, `EV-1e_output.txt:326`) shows `Workbooks -> non-null <System.__ComObject>` on the same machine/build, both cold-activated (STAGE A/C) and ROT-attached after a real `et.exe` document was opened externally (STAGE D, line 772). The two readings are not actually contradictory once read carefully: EV-1d's probe checked `Workbooks` immediately after `new Application()`/`GetActiveObject`, with `ActiveWorkbook`/`ActiveSheet` all null — i.e. a "cold" app object with no document context yet. EV-1e's STAGE C probe (same cold state) *did* get a non-null `Workbooks`, so the property itself binds; what's unreliable is whatever the previous worker's `Workbooks.Open(...)` call did with it (T5.1b's already-rejected argument-permutation fix). The old code (pre-patch) called `GetProp(_app, "Workbooks")` unconditionally, with no null check before handing the result to `CallMethod(workbooks, "Open", ...)` — if `Workbooks` ever *does* come back null on some WPS session/build, that call would throw `NullReferenceException` from inside `InvokeMember`, not a clean `EngineFoundOpenFailed`. My patch treats "the property occasionally binds but must never be trusted un-checked" as the operative lesson from both pieces of evidence, per the task's own instruction (T5.1c.md, "Locked facts").

**Priority order implemented, per task §"Required implementation shape":**
1. `ActiveWorkbook` if already non-null — `TryGetProp(app, "ActiveWorkbook", ...)`. Justified by EV-1e STAGE B (`dispid=308`, known name) — the surface exists and is queryable even though it reads null pre-open (STAGE C: `ActiveWorkbook -> returned NULL`); trying it first is free and correct once a workbook is already open in-session.
2. `ActiveWindow` → `.Workbook` — `TryGetProp(app, "ActiveWindow", ...)` then `TryGetWorkbookFromWindow`. Justified by EV-1e STAGE B (`dispid=759`, known name). `ActiveWindow` is a documented Excel-model member (window→workbook is a real Excel object-model relationship: `Window.Workbook`, per Microsoft Learn's `Excel.Window` interface) — this is not an invented alias, it is the standard route from a window object to its owning workbook. EV-1e never got as far as testing this specific downstream property (STAGE D only re-checked `ActiveWorkbook`/`Workbooks`/`Documents`/`Sheets`), so this hop is included per the task's explicit instruction ("insofar as it helps reach an already-open workbook surface") and fails safe (try/catch, released on exit) if the member turns out absent on this build.
3. `Workbooks` collection, `Open`/`_Open` — this is the binding authority from EV-1e STAGE E: the `Workbooks` object's own `ITypeInfo` (GUID `000208db-...`, type name `Workbooks`) lists exactly `Open memid=1923 cParams=15` and `_Open memid=682 cParams=13` as the callable open members (lines 664-670). I changed `TryOpenWorkbook` to call these two member names in that priority order, each with the *exact* parameter count the type info reports (15 and 13 total slots, filename + `Type.Missing` padding) — not a fixed small set of "more permutations" as the previous, now-forbidden direction did (that fix tried `{1,2,3,5}`-length arg arrays against a single `"Open"` name guess). This is a surface-specific fallback directly justified by EV-1e's own type dump, per the task's exception clause ("acceptable only if directly justified by EV-1e-discovered members on the `Workbooks` collection itself").
4. `Documents`/`ActiveDocument` — **not implemented**. EV-1e STAGE B confirms both are `UNKNOWN_NAME` (`DISP_E_UNKNOWNNAME`) on this machine (lines 289-290, 711-712). No justification exists to add them.
5. Application-level `Open`/`OpenFile`/`OpenWorkbook`/`OpenDocument` — **not implemented**. EV-1e STAGE B confirms all four are `UNKNOWN_NAME` (lines 314-321, 736-743). No justification exists to add them.

**Binding-flags/open-invocation-shape change and why.** Two changes, both surface-tied to EV-1e, not argument-guessing:
- `CreateWorkbookOpenArgs` no longer takes a "how many extra `Type.Missing` slots beyond the filename" count; it now takes the *total* parameter count for the target member (15 for `Open`, 13 for `_Open`), matching `cParams` from the STAGE E type dump exactly. This removes the old code's four arbitrary lengths (`{1, 2, 3, 5}` total slots) that had no basis in any discovered member signature.
- Added `TryGetProp` — a defensive wrapper used everywhere a property is read from the app object (`ActiveWorkbook`, `ActiveWindow`, `Workbooks`). It null-checks and swallows `DISP_E_UNKNOWNNAME`/other binder exceptions uniformly, replacing the previous single unguarded `GetProp(_app, "Workbooks")` call. Debug output for each surface distinguishes: "unavailable or null" (property absent or bound-but-null, from `TryGetProp`'s own trace), "returned null" (member called but no workbook), and per-attempt bind/open failure (`Workbooks.Open`/`Workbooks._Open` exception messages) — satisfying the task's "missing surface, null surface, bind failure, and open failure" distinction requirement.
- Did **not** change `BindingFlags` (`BindingFlags.GetProperty | BindingFlags.Public | BindingFlags.Instance`, etc.) — EV-1e's STAGE C/E results (e.g. `Range -> ERR: Number of parameters specified does not match the expected number.`, `Item -> ERR: ...`) are argument-count mismatches, not binder-flag mismatches; nothing in the evidence implies `GetProperty`/`InvokeMethod`/`SetProperty` flags are too narrow. Widening them without evidence would violate the task's "adjust only if the change is directly tied to the evidence" constraint.

**Fail-fast behavior.** `AcquireWorkbookSurface` returns `null` if none of the three surfaces yield a workbook; `Open()` then logs `EngineFoundOpenFailed (no usable workbook surface from ActiveWorkbook, ActiveWindow, or Workbooks)` and returns `false` — same swallow-and-return-`false` contract as before and as `MsExcelWorkbookPdfExporter.Open` (`MsExcelWorkbookPdfExporter.cs:38-54`). No new exception path was introduced; the `_app` field is still retained on `EngineFoundOpenFailed` so `Dispose()` can still `Quit()` a live app object, unchanged from the pre-patch contract (lines 263-265, unedited).

**Provider isolation / R9 preserved.** `WpsWorkbookPdfExporter.cs` still contains zero references to `Microsoft.Office.Interop.Excel` and zero `Xl*` enum names — verified by `Grep -n "Interop|Xl[A-Z]"` against the file: the only two hits are `using System.Runtime.InteropServices;` (line 5, the .NET COM interop namespace, not Office Interop) and a doc-comment string literal describing what the file must *never* reference (line 15). All COM access remains via `Type.GetTypeFromProgID` + `Activator.CreateInstance` + `InvokeMember`, unchanged.

## Decision

`WpsWorkbookPdfExporter.Open` now acquires the workbook surface in the order `ActiveWorkbook` → `ActiveWindow.Workbook` → `Workbooks.Open`/`Workbooks._Open`, every hop null-checked via a shared `TryGetProp` helper, with `Workbooks.Open`/`_Open` parameter counts corrected to match the exact `cParams` (15/13) discovered on the `Workbooks` type info in EV-1e. No `Documents`/`ActiveDocument`/application-level `Open` path was added, consistent with those names being confirmed absent in both EV-1d and EV-1e. The provider still fails fast and swallows to `false` when no surface yields a workbook, with debug output distinguishing missing/null surface, bind failure, and open failure. File remains late-bound only; local build passes.
