## Questions you must answer, each with a verdict and a reason

1. **Interop leak.** Can `WpsWorkbookPdfExporter.cs` be written with no `Microsoft.Office.Interop.Excel`
   using-directive, no `Xl*` enum, and no early-bound COM type, while still satisfying the session
   interface locked in `T1.1`? If any interface member forces an Interop type into a signature, that is
   a design defect — report it and propose the fix (for example: the interface must expose only
   `string`, `bool`, and `IReadOnlyList<string>`, never a `Range` or `Worksheet`).
2. **Interface neutrality.** Inspect the locked signature list for any type that belongs to either
   engine. The interface must be engine-agnostic by inspection, not by convention.
3. **`EmbedInteropTypes=true` interaction.** The `COMReference` at `ArcTool.Core.csproj:20-28` embeds
   the Excel interop types into the assembly. Confirm that moving the Interop calls from
   `Services/ExcelInteropService.cs` into `Services/Excel/MsExcelWorkbookPdfExporter.cs` needs no
   csproj change, and that the SDK-style glob picks up the new folder automatically. If you conclude the
   csproj must change, return `BLOCKED` — no task in this package owns that file (see manifest lock
   summary).
4. **Behavior parity feasibility.** Walk contract R11 item by item and state whether each survives the
   planned decomposition. Flag anything that cannot be preserved exactly, especially: the temp-PDF
   `finally` cleanup moving from provider to coordinator, and `ExcelSyncEngine.cs:162` still being able
   to throw its user-facing `InvalidOperationException` on open failure.
5. **Missing-engine diagnostics.** Confirm the coordinator can distinguish "no engine installed" from
   "engine installed but export failed", given the failure semantics from `T1.2`. Without that split,
   users on a WPS machine get a misleading message.
6. **Unknowns that do not block.** List every WPS uncertainty that must be carried as UNVERIFIED into
   Phase 5 rather than blocking the code work. WPS (12.1.0.28032, `KET.Application` resolving) is now
   installed on this machine, so `EV-1`/`EV-2`/`EV-3` can all run here — but no evidence has actually
   been collected yet at this gate. Treat the WPS branch as still additive and non-blocking: even with a
   local WPS install available, the MS branch is what must be fully verifiable for `GO`, and open WPS
   questions route to Phase 5 rather than stalling Phase 2-4. Say so explicitly if you agree, or argue
   otherwise.

## Verdict rules

- `GO` — all six answered, no design defect, csproj untouched, R11 preserved with at most documented
  and acceptable relocations.
- `NO_GO` — a design defect exists that cannot be fixed inside this package's scope. Name it, name the
  minimum change that would clear it.
- `BLOCKED` — the plan requires writing a file no task owns, or a fact needed to decide is unobtainable
  without runtime access.

## Acceptance condition

UNVERIFIED carry-forward list.
