## 1. The three labels (frozen — use verbatim thereafter)

Scope of the vocabulary: it classifies the **runtime behavioral outcome of one Quick Dimension run
on one case**. It does not classify build results, tooling problems, or orchestration states.

- **Supported** — the run produces a dimension whose **every segment matches the predicted station
  delta within 0.1 mm**, with **all audit gates `true`** in `<ChainCreationAudit>`, and
  `referenceOrderRelation` is `Exact` or **complete** `Reversed`. Segment deltas are compared
  against the pre-committed prediction/oracle (contract R8), which is derived from projected
  stations on the wall axis (contract section 3: stations are physical projected stations in Revit
  internal feet; millimetres are presentation only, so the 0.1 mm tolerance is applied on the
  presented value of the same physical delta).
- **Unsupported-by-design** — **no dimension**, or a **deliberately reduced** dimension, where the
  reduction was predicted for this case before the run; the outcome is **announced by an honest
  diagnostic or dialog**; there is **no crash**; and there is **no silently wrong value** — every
  segment actually emitted is still within 0.1 mm and every dropped candidate is accounted for by a
  diagnostic (e.g. `DuplicateStation` for candidates colliding within `DuplicateTolerance`, or the
  `Grid` disabled diagnostic).
- **Defect** — **anything else**: a wrong segment value, a silent drop, a crash, a misleading
  diagnostic or dialog, any audit gate `false`, or a `Mismatch` order relation.

`Defect` is defined as the complement of the other two. It is never chosen by sentiment; it is what
remains when neither positive definition is fully satisfied.

## 2. Decision procedure (deterministic, run top-down)

### 2.1 Observable signals

| Id | Signal | Source of truth |
|---|---|---|
| `S0` | Evidence complete for this case? (one combined XML for the run, created-dimension id or explicit no-dimension outcome, dialog text if any) | operator evidence forwarded by the master |
| `S1` | Dimension created? (`yes` / `no`) | created dimension id, or explicit no-dimension outcome |
| `S2` | Every emitted segment within **0.1 mm** of the pre-committed prediction | prediction/oracle vs measured segment values |
| `S3` | **All** audit gates `true` | `<ChainCreationAudit>` (order/identity/owner/segment gates, incl. `elementIdMatchesReferenceOwner`) |
| `S4` | `referenceOrderRelation` value | `<ChainCreationAudit>` — one of `Exact`, complete `Reversed`, `Mismatch` |
| `S5` | Output honest? Every deviation from the full expected chain is announced by a diagnostic or dialog, and no text implies capability the flow does not have | diagnostics + dialog text |
| `S6` | Crash / hang? (`yes` / `no`) | operator observation, dialog, optional journal excerpt |
| `P` | Pre-committed class for this case: `predicted-Supported` or `predicted-Unsupported-by-design` | the session's written prediction, fixed **before** evidence (R8) |

`P` is read from the prediction, never inferred from the evidence.

### 2.2 Decision table

| Step | Condition | Verdict |
|---|---|---|
| 1 | `S0` = evidence missing or incomplete for any signal the step below needs | **`BLOCKED`** (not a label — see section 4) |
| 2 | `S6` = crash/hang | **Defect** |
| 3 | `S4` = `Mismatch` | **Defect** |
| 4 | `S5` = dishonest/misleading output | **Defect** |

Steps are evaluated in order; the first matching step decides. Steps 2–4 are hard `Defect` gates and
are never overridden by a later step.

Note on audit availability: per contract section 3, audit append is failure-isolated — a committed
dimension still counts as command success. If the dimension committed but `<ChainCreationAudit>` is
absent, `S3`/`S4` are unobservable, so the case is **`BLOCKED`** on a re-run producing the combined
XML. It is not `Supported` (the conjunction is unproven) and not `Defect` (nothing wrong was shown).

## 3. Where `referenceOrderRelation` fits, and the strict audit policy

- `Exact` — acceptable for **Supported**.
- Complete `Reversed` — equally acceptable for **Supported**. A whole-chain reversal is an
  orientation artefact, not an ordering error.
- `Mismatch` — **forces Defect**, at step 3, before any other consideration.

**Contract rule R3, restated and never to be weakened:** `GetReferenceOrderRelation` keeps exactly
`Exact`, complete `Reversed`, and `Mismatch`. There is **no `LocalPairSwap` whitelist** and **no
unordered-set identity matching**. No judging task may introduce a fourth relation, accept a local
pair swap as `Exact`/`Reversed`, or compare reference sets ignoring order. A newly observed local
swap is a **fresh regression** with its own evidence (contract section 1, *What this mission is
NOT*), never a reason to relax the audit.

## 4. Missing or incomplete evidence is `BLOCKED`, not `Defect`

Absent, partial, or unreadable evidence proves nothing about product behavior. Per
`05_RESULT_SCHEMA.md`, that is the orchestration state **`BLOCKED`**: "the task cannot proceed
without missing evidence, a missing upstream result, or a denied tool call. Name the missing input
precisely."

A judging task in that position MUST return `BLOCKED` and name the missing operator input — for
example: the combined Quick Dimension XML for run *N* (one per run), the created dimension id or an
explicit no-dimension statement, the `<ChainCreationAudit>` element, the dialog text, or the
pre-committed prediction for the case. It must not guess, must not average partial runs, and must
not convert an unproven case into either a `Defect` or a `Supported`.

`BLOCKED` is a state of the *task*, not a fourth verdict for the *case*. The case simply stays
unclassified until evidence arrives. Agents have no file access to the operator machine
(`C:\Users\ADMIN\Desktop\PA4\` is out of reach), so `BLOCKED` is the normal, expected route for any
gap — never a fallback interpretation.

## 5. Mutual exclusivity and joint exhaustiveness

**Exhaustive.** The table in 2.2 partitions the outcome space on a fixed sequence of binary or
finite-valued signals: `S6` (2 values) → `S4` (3 values) → `S5` (2) → `S1` (2) × `P` (2) → the
conjunction `S2 ∧ S3` (2). Every branch terminates in a labelled leaf, and `Defect` is defined as
the complement of the two positive definitions, so no observed outcome can fall outside the three
labels. Cases where a needed signal has no observed value are removed from the space *before*
classification by step 1 (`BLOCKED`), so they are not counterexamples to exhaustiveness — they are
simply not yet observations.

**Mutually exclusive.** Three independent reasons:
1. The procedure is an ordered first-match table; exactly one step fires per case, so exactly one
   label is emitted.
2. `Supported` requires a created dimension (`S1` = yes) satisfying `S2 ∧ S3 ∧ S4 ∈ {Exact,
   complete Reversed}`. `Unsupported-by-design` requires either `S1` = no, or a reduced output for a
   case whose pre-committed class is `predicted-Unsupported-by-design`. The `S1` = no branch is
   disjoint from `Supported` by `S1` alone. The reduced-output branch is disjoint from `Supported`
   because the two are separated by `P`, which is fixed before observation and cannot take both
   values. The single case where a `predicted-Unsupported-by-design` case yields a full correct
   chain is resolved once and only at step 11, so it does not create an overlap.
3. `Defect` is the set complement of the union of the two positive definitions, hence disjoint from
   both by construction. `Mismatch`, crash, and dishonest output are excluded from both positive
   definitions explicitly, so they cannot also satisfy either.

## 7. Forbidden reinterpretations

- No new labels. Three terms only: `Supported`, `Unsupported-by-design`, `Defect`.
- No `Partially supported`, `Mostly supported`, `Acceptable`, `Known limitation`, or similar.
- Never soften a `Defect` into `Unsupported-by-design` because the case looks hard, rare, or
  edge-ish. Difficulty is not a design decision.
- Never promote `Unsupported-by-design` to `Supported` because output was "close enough". The
  tolerance is **0.1 mm** per segment; there is no second, looser tolerance.
- Never treat absent evidence as proof of either label. No evidence → `BLOCKED`.
- Never accept a `Mismatch` order relation under any label but `Defect`, and never add a
  `LocalPairSwap` whitelist or unordered-set matching to make one pass (R3).
- Never rewrite a prediction after seeing evidence to make a case fit a nicer label (R8). A
  falsified prediction is recorded as falsified.
- Never use a Grid or scope argument to excuse a wall-axis behavioral difference.
- Never let an audit-append failure be read as `Supported`; unobservable gates are `BLOCKED`.

## 8. Final decision

**PASS.** The three labels are operational, mutually exclusive, jointly exhaustive over the
observable outcome space, and directly usable by `T2.4`, `T3.5`–`T3.8`, `T4.4`, and `T6.7` without
reinterpretation. The 0.1 mm per-segment tolerance and the all-gates-`true` audit requirement are
preserved, and the strict `Exact` / complete `Reversed` / `Mismatch` policy (R3) is restated as
non-weakenable.
