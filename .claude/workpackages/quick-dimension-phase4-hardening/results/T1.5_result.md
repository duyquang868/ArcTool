## 2. Why `dotnet build` is not approved here

`dotnet build` is rejected for this repo on a recorded compatibility ground, not a preference:

- it fails with `MSB4803: ResolveComReference is not supported on the .NET Core version of MSBuild`.

The project carries COM-reference resolution (Revit/Office-era native and COM interop surface), which the .NET Core version of MSBuild does not support. Full Visual Studio MSBuild does. So the approved route is the section 7 command above, and `dotnet build` must not be substituted "just to check quickly" — its failure is a toolchain artefact and carries no information about the correctness of the code under test.

## 4. What counts as a real build failure for this package

Clean separation of warnings from errors:

| Build output | Verdict |
|---|---|
| `0 errors`, no warnings | `PASS` |
| `0 errors`, only `CS8600` / `MSB3246` known-benign noise | `PASS` |
| `0 errors`, other warnings present | `PASS`, with the new warnings reported |
| `1+` errors | real build failure |
| Approved MSBuild path cannot be resolved or executed | `BLOCKED`, not a failure verdict |

A real build failure for this package is exactly: the approved MSBuild command runs and reports one or more errors. Warning count is never a failure criterion. Contract section 7 states the rule positively: a build task reports `PASS` on `0 errors`.

For the unresolvable-path case, first attempt `vswhere` per contract section 7; if MSBuild still cannot be resolved, the downstream build task returns `BLOCKED` naming the missing MSBuild path as the operator-supplied input, per the `T1.4` handoff principle that absence of evidence is an orchestration state and never a product verdict. It must not fall back to `dotnet build`.

## 5. Boundary preserved: T1.4 runtime vocabulary does not apply to build outcomes

`T1.4` froze `Supported`, `Unsupported-by-design`, and `Defect` to classify the runtime behavioral outcome of one Quick Dimension run on one case. That vocabulary has no jurisdiction over build outcomes.

Build outcomes are reported only with the orchestration states from `05_RESULT_SCHEMA.md`: `PASS`, `BLOCKED`, `NO_GO`.

Concretely:
- a compiler warning is not a `Defect`;
- a `0 errors` build is not `Supported`;
- a build with errors is a build failure reported through the envelope, not an `Unsupported-by-design` case;
- a missing MSBuild path is `BLOCKED`, not any runtime label.

The two vocabularies stay disjoint: runtime labels describe product behavior observed from operator evidence; envelope states describe task/orchestration outcome, which is what a build produces.
