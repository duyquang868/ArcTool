## 1. Scope anchor (why every variant is predicted the same way)

Per shared contract §3 and §5:
- `CollectWallAxisCandidates` (`QuickDimensionReadOnlyEngine.cs:126-127`) emits a `Grid` disabled diagnostic **before doing anything else** — Grid is unconditionally excluded from the wall-axis main flow, regardless of grid geometry, view state, or curve type.
- `QuickDimensionOptions.IncludeGrids` (`:68`) gates only the **deprecated** two-point intersection path, which is out of scope for Session 4.3 and for the whole package (§1, "What this mission is NOT").
- Session 4.3 is executed as the roadmap's *second sentence only*: "Ensure the MVP fails safely where support is not intended." Reading it as "make grid dimensioning work" would contradict the locked scope (§5).

Consequence: this matrix does not test whether grids can be dimensioned. It tests whether the disabling behavior is **robust** — i.e., whether it holds regardless of grid curve type or view-display state, with no crash, no silent wrong value, and no accidental activation of the deprecated `IncludeGrids` path. The predicted classification for all four variants, per the acceptance vocabulary in §6, is **Unsupported-by-design**, contingent on: an honest `Grid` disabled diagnostic appearing, no dimension segment attributable to a grid, and the wall-axis chain (anchors/openings/mid-run joints) still resolving normally for whatever host wall is selected in the same run.

A **Defect** verdict on any variant would be: the disabling diagnostic does not fire, the run crashes or throws when a grid of that variant is present, the final chain is corrupted because of grid presence, or `IncludeGrids`'s deprecated path activates unexpectedly and silently alters the result.

## 2. The four variants

### GRID-V1 — Straight grid
**Intent:** baseline safe-failure case. A standard, fully visible, straight (`Line`-based) grid, uncropped, unhidden, present somewhere in the same view as the selected host wall.

**Why worth testing despite Grid being disabled in the main flow:** confirms the null case — that ordinary grid presence in the model/view has zero effect on wall-axis candidate collection, the disabling diagnostic fires cleanly, and nothing about grid bystander content perturbs the walls/doors/windows chain that Session 4.2 already classified. This is the control the other three variants are compared against.

**Minimum setup facts to preserve:**
- The host wall selected for the Quick Dimension command is a known straight wall (ideally reused from the clean fixture in Session 4.1 or a Session 4.2 fixture) — the grid must be bystander content, not the selection target.
- Confirm via Revit's own Properties/Type Selector that the grid's curve is a straight line (not accidentally arc-based).
- Confirm the grid is not cropped or hidden in the active view for this run (so this run is a clean control, distinguishable from V2/V3).
- Capture the combined XML for this run and confirm it contains a `Grid` disabled diagnostic entry, independent of the final chain result.

### GRID-V2 — Cropped grid
**Intent:** a straight grid whose displayed extent is cut short by the active view's crop region, so the grid element exists in the model with its full model extents but only a partial line renders in view.

**Why worth testing despite Grid being disabled in the main flow:** the risk this variant targets is a code path that derives grid geometry from **view-visible** extents (e.g. curves-in-view / crop-clipped bounding data) rather than model extents, and could behave differently — or throw — on a degenerate/zero-length in-view segment. Because the disabling diagnostic is supposed to fire "before doing anything else" for grids, this variant is a stress test of that ordering: it should be provably irrelevant whether the grid's in-view extent is full-length, partial, or effectively zero.

**Minimum setup facts to preserve:**
- Confirm the view's crop region is enabled and explicitly positioned so the grid line visibly crosses the crop boundary (partially inside, partially outside) — record the crop state deliberately, since it is easy to leave unset or reset between sessions.
- Confirm the grid's curve type is straight (isolate the cropping variable from the arc variable; do not combine V2 and V4 in one run).
- Same host-wall discipline as V1: the selected wall is unrelated to the grid and unaffected by the crop region.
- Capture the combined XML and confirm the `Grid` disabled diagnostic is present and identical in shape to V1's.

### GRID-V3 — Hidden grid
**Intent:** a straight grid that is hidden in the active view, either via element-level "Hide in View" or via the Visibility/Graphics override for the Grids category.

**Why worth testing despite Grid being disabled in the main flow:** the risk this variant targets is any code path that calls a `View`-dependent geometry or visibility API against a grid (e.g. attempting to read a grid's curve-in-view before checking whether the disabling diagnostic should short-circuit first). Revit APIs can throw for geometry queries against hidden/invisible elements in some contexts; this variant confirms the disabling diagnostic protects against that regardless of visibility state, and that hidden grids do not silently exempt themselves from — or otherwise alter — the disabling behavior.

**Minimum setup facts to preserve:**
- Record which hiding mechanism was used (per-element "Hide in View" vs. category-level Visibility/Graphics override) — they are different Revit code paths and only one should be tested per run unless the task owner explicitly wants both.
- Confirm the grid element still exists in the model (not deleted) and is only hidden in the specific view used for the Quick Dimension run.
- Same host-wall discipline as V1/V2.
- Capture the combined XML and confirm the `Grid` disabled diagnostic is present; note explicitly whether a hidden grid still produces a diagnostic entry (expected: yes, since exclusion happens before any per-element visibility check per §3/§5) or whether hidden grids are silently skipped before the diagnostic point (would still be Unsupported-by-design, but the shape of the diagnostic evidence would differ and must be recorded honestly rather than assumed).

### GRID-V4 — Arc grid
**Intent:** a curved (arc-based) grid line. Revit supports arc grids; this is the geometry type most structurally different from the wall-axis flow's straight-`Line`-only assumption (§3: `Wall.LocationCurve` must be a `Line`).

**Why worth testing despite Grid being disabled in the main flow:** this is the highest-risk variant for a crash rather than a clean diagnostic. If any code path attempted to project or parameterize a grid curve onto the wall axis before the disabling check, an arc curve is the type most likely to throw (arcs cannot be linearly parameterized the way a `Line` can, and axis-projection math written for lines can misbehave or throw on curved input). This variant is the strongest test that the "before doing anything else" ordering in `CollectWallAxisCandidates` is real and unconditional, not merely true for the straight-grid case that happens to resemble the wall axis geometry.

**Minimum setup facts to preserve:**
- Confirm in Revit that the arc grid was created and accepted without model corruption before running Quick Dimension — this is a Revit-side prerequisite unrelated to ArcTool and must be verified independently so a failure cannot be misattributed to the ArcTool command.
- Confirm the grid's curve type is arc-based via Properties/Type Selector, not merely "looks curved" in view.
- Same host-wall discipline as V1–V3: the selected wall stays straight and unrelated to the arc grid, per the locked scope that ArcTool's wall-axis flow only ever supports a straight host wall (§3) — the arc grid is bystander content only, never the selection target.
- Capture the combined XML and confirm the run completes (dimension created or an honest no-dimension outcome) with no unhandled exception, and that the `Grid` disabled diagnostic is present.
