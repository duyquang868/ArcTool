## 1. Source-verified mechanism (stronger than T4.1's claim — now confirmed at the line level)

`QuickDimensionReadOnlyEngine.CollectWallAxisCandidates` (`QuickDimensionReadOnlyEngine.cs:116-196`):

```
:126  // Grid is excluded from the wall-axis main flow by design.
:127  AddDisabledDiagnostic(diagnostics, QuickDimensionSourceType.Grid);
:129  ElementId? wallId = lineContext.SourceWallId;   // wall resolution happens AFTER the Grid diagnostic
```

Confirmed facts:
- The Grid disabled diagnostic is added **unconditionally and first**, before the selected wall is
  even resolved (`:129`), before any `FilteredElementCollector` for Grid elements runs, and before
  any per-grid property (curve type, crop state, visibility, hidden state) is read.
- `QuickDimensionGridCandidateCollector.CollectGridCandidates` (the only code that would touch grid
  curve/geometry) is **never called** anywhere inside `CollectWallAxisCandidates`. It is only called
  from the non-wall-axis branch (`:71`, guarded by `IncludeGrids` at `:68-79`), which is the
  deprecated two-point path and structurally unreachable when `lineContext.IsWallAxis` is true
  (`:61-66` returns before reaching `:68`).
- `AddDisabledDiagnostic` (`:417-426`) always emits the **same literal shape** regardless of caller:
  `Severity = Info`, `RejectedReason = None`, `SourceType = Grid`,
  `Message = "Grid collection is disabled by Quick Dimension options."` — this exact string does not
  mention "wall-axis" or "unsupported"; it is the generic "disabled by options" message reused for
  both the deprecated-path-disabled case and the wall-axis-unconditional-exclusion case. `T4.4` must
  match on this literal string (or the `Severity=Info, SourceType=Grid` diagnostic tuple), not on any
  wall-axis-specific wording, because none exists in source.

Consequence for prediction confidence: because the Grid-touching collector is never invoked in this
flow, none of the four variants' hypothesized risk mechanisms (crop-derived geometry, hidden-view API
calls, arc-curve linear projection) have a code path to trigger through **in this function**. This
raises confidence that all four variants converge on an identical outcome, but does not fully close
the question, because two collectors called later in the same flow — the mid-run wall aggregator
(`QuickDimensionWallAxisAggregatorService.CollectMidRunCandidates`) and the Door/Window collector
(`QuickDimensionDoorWindowCandidateCollector.CollectOpeningsAlongWallAxis`) — plus the XML log
builder (`QuickDimensionReadOnlyXmlLogService`) were **not read** in this task and could in principle
enumerate Grid elements independently for unrelated reasons (e.g. a view element inventory dump).
This is recorded as an open unknown, not assumed away.

## 2. Per-variant safe-failure prediction

All four variants share the identical predicted diagnostic shape and the identical "why," because
the exclusion point (`:127`) does not branch on grid count, curve type, crop state, or visibility.
Variants differ only in what a *contradicting* result would imply.

### GRID-V1 — straight, normal view (control)
- **Acceptable outcome:** no dimension segment attributable to the grid; combined XML diagnostics
  contain exactly one entry with `Severity=Info, SourceType=Grid, Message="Grid collection is
  disabled by Quick Dimension options."`; the wall/opening/mid-run chain resolves identically to a
  run with no grid present at all; no crash; command completes with either a committed dimension
  (from wall/door/window sources only) or an honest no-dimension outcome if those sources alone don't
  produce ≥2 distinct stations.
- **Defect if:** the diagnostic is missing, has wrong severity/sourceType/message, a created
  dimension segment's reference traces back to the grid element id, the wall/opening/mid-run chain
  differs from the no-grid baseline, or any unhandled exception occurs.
- **XML expectation:** one combined XML is always produced (contract §3, "one smoke run produces ONE
  combined XML"), independent of whether a dimension commits, because the diagnostics list is
  populated during the read-only collection phase regardless of downstream creation/audit outcome.
  Absence of any XML at all is itself an anomaly (crash before write, or an XML-write bug) — treat as
  needing investigation, not as "test not applicable."

### GRID-V2 — straight, cropped view
- **Acceptable outcome:** identical to GRID-V1 in every respect (diagnostic shape, no dimension from
  the grid, no crash), because no code in the wall-axis path reads the grid's in-view/crop-clipped
  extent.
- **Defect if:** same defect list as V1, plus specifically: any exception tied to a degenerate or
  zero-length in-view curve segment, or a crash that only reproduces when the crop boundary
  intersects the grid.
- **Non-defect but reportable difference:** if the diagnostic shape or timing differs from V1 without
  crashing or corrupting the chain (e.g. an extra unrelated diagnostic appears), that is evidence a
  code path *is* crop-sensitive after all — contradicting the static read in §1 — and must be reported
  to `T4.4` as a new finding, not silently folded into "still Unsupported-by-design." Only a corrupted
  chain, wrong dimension value, or crash converts this into a **Defect**.

### GRID-V3 — straight, hidden view (element-level or V/G override)
- **Acceptable outcome:** identical to GRID-V1 (diagnostic shape, no dimension from the grid, no
  crash), because the diagnostic fires before any per-element visibility check and the grid collector
  is never invoked to query hidden-element geometry.
- **Defect if:** same defect list as V1, plus specifically: a crash tied to querying a hidden
  element's geometry/curve-in-view, or the Grid diagnostic silently disappearing when the grid is
  hidden (would indicate visibility filtering happens *before* `:127`, contradicting the confirmed
  unconditional-first ordering in §1 — report as a finding regardless of whether it also crashes).
- **Setup-dependent evidence note:** record which hide mechanism was used (element `Hide in View` vs.
  category V/G override) per T4.1's setup facts; a difference in outcome between the two mechanisms
  would itself be a finding worth flagging even if neither is a Defect.

### GRID-V4 — arc, normal view
- **Acceptable outcome:** identical to GRID-V1 (diagnostic shape, no dimension from the grid, no
  crash), because `CollectGridCandidates` — the only code that would attempt to read or
  linearly-parameterize the grid's curve — is never invoked in the wall-axis flow. This is the
  variant with the least structural risk given the confirmed source (contrary to T4.1's framing of it
  as "highest-risk"): no arc-curve math ever executes.
- **Defect if:** any crash/exception occurs when an arc grid is present in the model/view during the
  command run. Before attributing any failure to ArcTool, first independently confirm (per T4.1's
  setup facts) that the arc grid itself is valid, uncorrupted Revit content — a Revit-side geometry
  failure on the grid itself must not be misattributed as an ArcTool defect.
- **XML expectation:** same as V1 — one combined XML, Grid diagnostic present and identically shaped.

## 3. Cross-variant defect list (explicit, applies to all four)

A result is a **Defect**, never softened to "acceptable safe-failure," if any of the following occur
on any variant:
1. A dimension is created and any of its segments derives from a Grid reference or Grid element id —
   **an accidentally created grid-attributable dimension segment is a Defect, never a success**, even
   if the segment's numeric value happens to look plausible.
2. The command crashes or throws an unhandled exception with a grid of that variant present.
3. The `Grid` disabled diagnostic (`Severity=Info, SourceType=Grid, RejectedReason=None`, message
   `"Grid collection is disabled by Quick Dimension options."`) is missing from the combined XML for
   that run.
4. The wall/opening/mid-run chain (stations, order, audit gates) differs from what the same host wall
   would produce with no grid present in the model/view at all.
5. The deprecated `IncludeGrids` two-point path activates and silently alters the result — this
   requires `lineContext.IsWallAxis` to be false, which should not happen for any of these four runs
   given the wall-axis selection discipline in T4.1's setup facts; if it happens anyway, that is a
   Defect in run setup interpretation, not a code defect, and must be re-run rather than reported as
   a Grid-support finding.

None of the four variants have a predicted path to a **Supported** classification (per shared-contract
§6 vocabulary) — that would require a committed dimension whose segments are grid-derived, which is
explicitly out of scope and, per item 1 above, is to be treated as a Defect regardless of numeric
correctness, not as an unexpected win.
