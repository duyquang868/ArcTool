## 0. Framing — read this before running anything

This is a **safe-failure** matrix, not a Grid-support test. `QuickDimensionCreateChainSmokeCommand`'s
selection filter accepts only a straight non-curtain `Wall` as the pick target — **a Grid can never be
picked as the command's selection target**. Do not try to select a grid; the command will not offer it.
Every grid in this matrix is **bystander content** that exists in the model/view while a straight wall
is picked and dimensioned. The question under test is only: does grid presence (of four different
kinds) change the command's behavior at all? The predicted answer for all four runs is **no** — grid
collection is disabled unconditionally before anything else runs (`T4.2` §1). Do not read "no dimension
uses the grid" as a bug; that is the expected and required outcome. Do not read a small side-effect on
the wall/door/window chain as automatically fine either — report any difference from the control run
(§5 below) even if nothing crashes.

Run order: `G1_V1` → `G2_V2` → `G3_V3` → `G4_V4`. Run `G1_V1` first; it is the control every other run
is compared against. Do not skip it or reorder it after the others.

Isolate one variable per run. Do not combine cropped and arc in the same run, do not combine hidden and
arc, and do not test two grid shapes in the same view/run. Each run tests exactly one grid
characteristic against the same wall-axis flow.

**Reuse the same host wall across all four runs where practical.** Use one straight, non-curtain wall
(the Session 4.1 clean fixture wall, or a Session 4.2 fixture wall) as the pick target for every run.
Do not change the wall, its openings, or its joins between runs — only the grid's shape/view-state
changes. This keeps the wall/opening/mid-run chain comparable across `G1_V1`..`G4_V4` and against the
V1 control, so any difference in outcome can be attributed to the grid variable, not to fixture drift.

## 2. Per-run setup and execution steps

### G1_V1 — straight grid, normal view (control)
**Setup:**
1. Place or reuse an existing straight grid somewhere in the same view as the host wall. It must be
   bystander content only — never select it as the command target.
2. In Revit, select the grid and check **Properties** to confirm its curve type is a straight line
   (not accidentally arc-based). Record this confirmation.
3. Confirm in the active view that the grid is **not** cropped and **not** hidden — this run is the
   clean baseline the other three are compared against.
4. Confirm the host wall is straight, non-curtain, and unrelated to the grid (not touching, not
   dimensioned from it).

**Execute:**
5. Run `QuickDimensionCreateChainSmokeCommand`.
6. Pick the host wall (the only valid pick target — the grid cannot be picked).
7. Pick a side (Left/Exterior or Right/Interior — keep the same side across all four runs unless a
   specific reason requires changing it; record which side was used).
8. Let the command complete (dimension created, or an honest no-dimension outcome).

### G2_V2 — cropped grid
**Setup:**
1. Use a straight grid (confirm curve type via Properties, same as G1_V1 step 2 — do not combine the
   cropped variable with the arc variable in this run).
2. Enable the active view's crop region and position it so the grid line visibly crosses the crop
   boundary (partially inside, partially outside the crop). **Record the crop region state
   deliberately** (on/off, and the fact that the grid crosses it) — this is easy to leave unset or
   reset between sessions and must not be assumed from memory.
3. Same host-wall discipline as G1_V1: wall is straight, unrelated to the grid, unaffected by the crop
   region.

**Execute:**
4. Same execute steps as G1_V1 (steps 5–8), same host wall, same side pick.

### G3_V3 — hidden grid
**Setup:**
1. Use a straight grid (confirm curve type via Properties).
2. Hide the grid in the active view using **one** of two mechanisms — element-level "Hide in View" or
   category-level Visibility/Graphics override for Grids. **Record which mechanism was used**; they
   are different Revit code paths and this run only tests one of them.
3. Confirm the grid element still exists in the model (not deleted) and is hidden only in this
   specific view.
4. Same host-wall discipline as G1_V1.

**Execute:**
5. Same execute steps as G1_V1 (steps 5–8), same host wall, same side pick.

### G4_V4 — arc grid
**Setup:**
1. Create or reuse an arc grid. **Independently confirm the arc grid is valid, uncorrupted Revit
   content** before running Quick Dimension — verify in Revit that the arc grid was accepted without
   model corruption. This is a Revit-side prerequisite unrelated to ArcTool; if this check is skipped
   and the run fails, the failure cannot be attributed to ArcTool.
2. Confirm the grid's curve type is arc-based via Properties/Type Selector, not merely "looks curved"
   in view.
3. Confirm the view state is normal (uncropped, unhidden) for this run — isolate the arc variable, do
   not combine it with cropped or hidden.
4. Same host-wall discipline as G1_V1–G3_V3: the selected wall stays straight and unrelated to the arc
   grid; the arc grid is bystander content only, never the selection target.

**Execute:**
5. Same execute steps as G1_V1 (steps 5–8), same host wall, same side pick.

## 4. Report this immediately — cross-run defect list (from `T4.2` §3, verbatim)

Any of the following, on **any** run, is a **Defect** — never soften it to "acceptable safe-failure":

1. A dimension is created and any of its segments derives from a Grid reference or Grid element id —
   an accidentally created grid-attributable dimension segment is a Defect, never a success, even if
   the segment's numeric value happens to look plausible.
2. The command crashes or throws an unhandled exception with a grid of that variant present.
3. The `Grid` disabled diagnostic (exact tuple/message above) is missing from the combined XML for
   that run.
4. The wall/opening/mid-run chain (stations, order, audit gates) differs from what the same host wall
   would produce with no grid present in the model/view at all.
5. The deprecated `IncludeGrids` two-point path activates and silently alters the result — this should
   not happen for any of these four runs given the wall-axis selection discipline above; if it happens
   anyway, treat it as a run-setup defect and re-run rather than reporting it as a Grid-support
   finding.

No run is predicted to reach a **Supported** classification. A committed dimension whose segments are
grid-derived is explicitly out of scope and is a Defect regardless of numeric plausibility, not an
unexpected win.
