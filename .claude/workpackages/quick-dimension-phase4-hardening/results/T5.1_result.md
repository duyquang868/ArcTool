## 1. Design objective and boundary

Session 4.4 exists to measure whether the current wall-axis read-only collection path is already fast enough for the intended one-wall interactive use, and only then decide whether a single-file optimization is justified. The instrumentation therefore needs to do exactly two things:

1. localize where wall-axis collection time is spent;
2. emit those timings through the already-existing read-only XML log path so EV-4 can be judged without introducing new UI, a new file format, or any runtime operator workflow beyond returning the normal combined XML.

Per shared-contract rule `R5`, the instrumentation must be behavior-neutral: no candidate output change, no audit change, no change in reference identity, no change in diagnostics, and no new Revit object creation in the measured path.

---

## 2. Recommended timing boundaries

The minimum timing set that can still identify a dominant cost center is:

1. **totalWallAxisCollectionMs**
   - Boundary: the full `CollectWallAxisCandidates(...)` wall-axis orchestration path.
   - Reason: establishes the total read-only collection cost that the operator experiences before XML logging and before dimension creation.

2. **wallEndAnchorCollectionMs**
   - Boundary: `QuickDimensionWallCandidateCollector.CollectSelectedWallEndAnchors(...)` only.
   - Reason: isolates the cost of the selected-wall anchor resolver from other collectors.

3. **midRunAggregationMs**
   - Boundary: `QuickDimensionWallReferenceProbeService.RunWallReferenceProbe(...)` plus `QuickDimensionWallAxisAggregatorService.CollectMidRunCandidates(...)`, measured as one contiguous block.
   - Reason: the aggregator depends on probe output and is only entered under narrow gates; timing them together matches the operator-visible "mid-run wall evidence" cost center and avoids introducing extra instrumentation surfaces in protected files.

4. **openingCollectionMs**
   - Boundary: `QuickDimensionDoorWindowCandidateCollector.CollectOpeningsAlongWallAxis(...)` only.
   - Reason: this is the most likely project-scale hotspot when many hosted openings exist; EV-4 needs to quantify its share of the total.

5. **duplicateStationReductionMs**
   - Boundary: `RemoveDuplicateStations(...)` inside the engine's final consolidation path.
   - Reason: this is the only post-collector normalization step explicitly mentioned by the task and can become noticeable if candidate volume grows.

This set is sufficient for `T5.5` because it allows a simple table: total versus each principal sub-stage, with enough resolution to decide whether one collector dominates or whether the time is too diffuse to justify a risky optimization.

## 3. Emission design

### Chosen emission path
Emit the timing values into the existing combined XML written by `QuickDimensionReadOnlyXmlLogService.WriteReadOnlySummaryLog(...)`.

### Why this path is preferred
- The operator already returns the combined XML for every evidence run.
- `BuildReadOnlyResultElement(...)` already holds the read-only summary payload, so timing data belongs there naturally.
- No new UI, dialog, file, or operator step is required.
- `T5.5` can judge EV-4 from the same artifact family already used throughout Phase 4.

### Concrete XML shape
Add a child block under `ReadOnlyResult`, for example:
- `<PerformanceTimings totalWallAxisCollectionMs="..." wallEndAnchorCollectionMs="..." midRunAggregationMs="..." openingCollectionMs="..." duplicateStationReductionMs="..." />`

Use invariant-culture numeric formatting consistent with the existing XML helpers. The exact element name can remain implementation-local, but it must satisfy these constraints:
- values are machine-readable without text parsing;
- names match the stage boundaries above;
- absent timing data is impossible in instrumented builds (the block is always present when wall-axis collection runs).

## 4. Neutrality argument

The design is concretely behavior-neutral if implemented as follows:

1. **Managed timing only around existing calls**
   - Capture timestamps immediately before and after existing method invocations already required by the current control flow.
   - No new branches that alter whether a collector runs.
   - No retry, no fallback, no changed gate.

2. **No new Revit object allocation in the measured path**
   - Timing capture uses managed primitives only.
   - The measured blocks continue to call the same existing Revit APIs in the same order.
   - No new `Document.GetElement`, geometry extraction, collector query, or reference resolution is introduced solely for measurement.

3. **No mutation of candidate or diagnostic data**
   - Timing values are stored separately from the candidate lists and diagnostics being produced.
   - The measured methods return the same values they returned before.
   - `RemoveDuplicateStations(...)` still decides duplicates exactly as before; only elapsed time is recorded around it.

4. **No change to audit behavior**
   - `GetReferenceOrderRelation(...)` remains untouched.
   - Chain creation audit consumes the same candidate/reference output as before.
   - Timing emission is read-only serialization, not audit logic.

5. **No change to command result semantics**
   - The command still succeeds or fails for the same reasons.
   - The XML remains an auxiliary evidence artifact, as it already is.
   - Adding attributes/elements to the summary does not alter dimension creation or post-commit audit gating.

## 5. Debug-appropriate / easy to remove later

The instrumentation should be implemented as a small, isolated payload carried by the read-only result and serialized only by the XML log service. That makes later disposition straightforward:
- `T6.4` can decide to remove it entirely or keep it behind an explicit debug gate;
- `T6.5` then needs to touch only the same two files already reserved in the lock summary;
- no collector file needs timing-specific cleanup if Session 4.4 ends with a NO_GO optimization decision.

The key design principle is containment: one engine capture surface, one XML emission surface, zero spread into collectors.
