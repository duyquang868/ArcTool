## 1. EV-4 objective

Collect the first measured Quick Dimension performance baseline on a project-like context that is materially denser than the clean fixture, using the instrumented build from `T5.3`, while keeping the runtime request small enough for one operator session.

The goal is not to prove an absolute benchmark number. The goal is to return comparable timings that let `T5.5` answer three questions:
1. what is the total wall-axis collection cost;
2. which measured stage is the largest contributor;
3. whether one stage dominates enough to justify a single-file optimization.

## 2. Operator runbook

### 2.1 Choose the test context
Pick one larger project-like Revit context that is meaningfully denser than the clean fixture used in Session 4.1.

Before running, record these three scale descriptors for that exact context:
- wall count
- door + window count
- view element count

These counts do not need to cover the whole project if the test is intentionally view-scoped, but they must describe the actual context in which the command is run.

### 2.2 Fix the run target
For the measured run set, keep the following fixed across all measured runs where practical:
- the same active view
- the same selected host wall
- the same side pick / shell choice
- the same visible scene state

The purpose is comparability. `T5.5` should be able to treat `EV4_M1..M3` as repeated measurements of one scenario, not three different scenarios.

### 2.3 Run order
Run `QuickDimensionCreateChainSmokeCommand` four times total in this exact order:
1. `EV4_WARMUP`
2. `EV4_M1`
3. `EV4_M2`
4. `EV4_M3`

Interpretation:
- `EV4_WARMUP` is a warm-up run only. Its timing values are not the numbers of record.
- `EV4_M1..M3` are the measured runs of record.

Why a warm-up run is required:
- it reduces the chance that the first measured sample is dominated by one-time setup effects;
- it makes the remaining three samples more comparable for variance judgment.

### 2.4 What must appear in the XML
Each run should produce the normal combined Quick Dimension XML.

For the measured runs `EV4_M1..M3`, confirm the XML contains:
- `ReadOnlyResult`
- child block `PerformanceTimings`
- timing attributes:
  - `totalWallAxisCollectionMs`
  - `wallEndAnchorCollectionMs`
  - `midRunAggregationMs`
  - `openingCollectionMs`
  - `duplicateStationReductionMs`

If a measured run does not contain this timing block, that run is not acceptable for `T5.5`.

## 3. What to return

Return one evidence bundle covering all four runs, labeled exactly as follows:
- `EV4_WARMUP`
- `EV4_M1`
- `EV4_M2`
- `EV4_M3`

Required return items:
- the three scale descriptors for the chosen context:
  - wall count

- run-to-file mapping for `EV4_WARMUP`, `EV4_M1`, `EV4_M2`, `EV4_M3`
- combined XML path for each run
- created dimension id or explicit no-dimension outcome for each run
- explicit confirmation that `EV4_M1..M3` used the same wall, same side pick, and same view context

Optional but useful:
- screenshot(s)
- journal excerpt(s)

Do not hand EV-4 to `T5.5` until all of the following are true:
- all four runs are present and labeled;
- `EV4_M1..M3` each contain the timing block;
- the five expected timing attributes are present in each measured XML;

- the measured runs are comparable by construction.
