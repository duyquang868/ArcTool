2. Namespace decision.
   - Current files use active namespaces aligned to their old folders: `ArcTool.Core.Commands`, `ArcTool.Core.Models`, `ArcTool.Core.Services`.
   - Under SDK-style compilation, namespace values do not have to match folder names, but keeping the old namespaces would leave the archived QD code still living in active public namespaces and still satisfying type references if any survive.
   - Retirement intent is cleaner if moved files adopt archive namespaces:
     - command files -> `ArcTool.Core.Archive.QuickDimension.Commands`
     - model files -> `ArcTool.Core.Archive.QuickDimension.Models`
     - service files -> `ArcTool.Core.Archive.QuickDimension.Services`
   - Because command files reference model/service namespaces and service files reference model namespaces, T2.3 and T2.4 should update internal `using` statements consistently during the move.
   - This change reduces accidental future coupling: any leftover active reference will fail clearly at compile time instead of silently binding to archived types through old namespaces.

3. csproj impact under SDK-style rules.
   - `ArcTool.Core.csproj` is plain SDK-style and contains no explicit `<Compile Include=...>` or `<Compile Remove=...>` entries for source folders.
   - Default SDK-style behavior includes `**/*.cs` under the project directory, so moving QD files into `ArcTool.Core/Archive/...` keeps them compiled unless excluded.
   - Therefore csproj changes are likely needed if the retirement goal is to archive source in-repo but remove it from the active build surface.
   - Minimal expected T2.5 change: add one compile exclusion for the archive subtree, e.g. an ItemGroup with `<Compile Remove="Archive\QuickDimension\**\*.cs" />`.
   - No other csproj edits appear necessary from the current file structure.

4. Minimal active-source cleanup sequence.
   - T2.2 must run first and only remove the seven QD `PushButtonData` registrations from `App.OnStartup` in `ArcTool.Core/App.cs`. This removes the live UI surface before any source moves.
   - T2.3 should then move only the seven command files into `Archive/QuickDimension/Commands/` and rewrite each file namespace/usings to the archive namespace plan. No other feature commands should change.
   - T2.4 should next move the eight model files and fifteen service files into their archive subfolders and rewrite namespaces/usings so the archived QD code remains internally coherent.
   - T2.5 should finish by excluding `Archive/QuickDimension/**/*.cs` from compilation in `ArcTool.Core.csproj`, then do only fallout cleanup required by the move strategy.

5. Recommended edit order and reasoning for T2.2 → T2.5.
   - `T2.2` first: remove startup registrations while source paths are still stable and before any namespace churn.
   - `T2.3` second: relocate command entry points after the UI no longer points at them.
   - `T2.4` third: relocate supporting models/services after commands, because commands are the outermost surface and their usings can be updated once against the final archive namespaces.
   - `T2.5` last: apply the compile exclusion only after all moves are complete; doing it earlier would make moved files disappear from the build mid-migration and obscure whether namespace/usings are internally consistent.

## Decisions

- Archive destination: `ArcTool.Core/Archive/QuickDimension/{Commands,Models,Services}/...`.
- Namespace policy: update moved files to archive-specific namespaces rather than preserving `ArcTool.Core.Commands/Models/Services`.
- csproj policy: expect one minimal SDK-style compile exclusion for `Archive/QuickDimension/**/*.cs`.
- Execution order: `T2.2` ribbon cleanup -> `T2.3` command move -> `T2.4` model/service move -> `T2.5` csproj exclusion/cleanup.

## Open questions

- None blocking at design level. The only implementation-sensitive point is whether any non-QD source still references QD types; if so, T2.5 should document the compile break precisely rather than broaden scope.
