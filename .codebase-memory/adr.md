## PURPOSE
Record stable architecture decisions that should guide future ArcTool implementation, especially Quick Dimension and Revit API feature work.

## STACK
ArcTool.Core targets Autodesk Revit 2026 API with C# / .NET 8.0, WPF, and limited WinForms. Quick Dimension production contracts live under `ArcTool.Core/Models`; production read-only geometry helpers and collectors live under `ArcTool.Core/Services`.

## ARCHITECTURE
Quick Dimension Phase 2 is a read-only engine boundary. Phase 1 spike models/services remain evidence and must not be mutated into production contracts. Production QD models are centralized in `QuickDimensionContract.cs`: options, line context, candidates, diagnostics, per-source summaries, and read-only result. Candidate contracts may carry `ElementId`, `Reference`, `XYZ`, strings, enums, and scalar values, but must not retain live Revit `Element` objects across service boundaries. `QuickDimensionGeometryService.cs` is the transaction-free/document-free math boundary for Phase 2; it must not collect elements, open transactions, or call `NewDimension`. Dimension creation begins only in Phase 3.

### ADR-2026-06-11: Quick Dimension pivots from cross-cutting intersection to wall-axis projection
Status: ACCEPTED and implemented in the Phase 2.6 read-only smoke path as of 2026-07-12.
Decision: The Quick Dimension MVP input model changes from "user draws a dimension line across the plan" to "user selects ONE host Wall, then picks a side (left/right)". The selected wall's `LocationCurve` (Line only in MVP) IS the dimension axis, even when the wall is skewed in plan. The tool no longer asks the user to draw a dimension line. References are gathered ONLY from the selected wall: the wall's two end anchors plus every Door/Window opening hosted in that wall, each opening contributing BOTH left and right jamb references. All reference points are PROJECTED onto the wall axis (signed parameter along the axis) and ordered to build the chain. A second user pick on the left or right of the wall sets the dimension placement side (side sign), captured in the contract from Phase 2 so Phase 3 placement has enough information.
Rationale: User confirmed the desired result measures openings ALONG a wall, which is how Revit "dimension along a wall" behaves. The previous intersection model answered "what does the drawn line physically cross", which structurally cannot return both jambs of an opening and rejects walls parallel to the line — the opposite of the requirement. This pivot resolves the observed Window collected-but-accepted=0 and Door single-jamb symptoms at the model level rather than patching collectors.
Implementation: `QuickDimensionLineContext.CreateFromWallAxis()` builds the axis from selected Wall `LocationCurve` endpoints and computes `SideSign` from the side pick. `QuickDimensionReadOnlySummaryCommand` uses `Selection.PickObject(ObjectType.Element, ISelectionFilter, string)` for the wall and `Selection.PickPoint(ObjectSnapTypes.None, string)` for side placement, rejecting curtain/non-line walls and ambiguous side picks. `QuickDimensionReadOnlyEngine` dispatches `IsWallAxis` contexts to selected-wall-only collection. `QuickDimensionWallCandidateCollector.CollectSelectedWallEndAnchors()` extracts the wall start/end anchors from wall geometry planar end faces with `Options.ComputeReferences = true`; Revit 2026 `HostObjectUtils` exposes `GetSideFaces`, `GetTopFaces`, and `GetBottomFaces`, not `GetEndFaces`, so wall ends must not use a non-existent utility method. `QuickDimensionReferenceStrategy.WallEndFace` records this anchor strategy separately from legacy `WallSideFace`. `QuickDimensionDoorWindowCandidateCollector.CollectOpeningsAlongWallAxis()` filters hosted openings by selected host wall id and projects both left/right jamb candidates onto the wall axis.
Consequences: `QuickDimensionCandidate.ParameterOnDimensionLine` means "projected coordinate on wall axis" in the main flow. Grid and other-wall sources drop out of the main flow and are explicitly disabled by the projection dispatch; they may return later as an opt-in legacy cross-cutting path. The intersection path (`TryIntersectSegmentWithDimensionLine2D`) and the parallel guard (`IsNearlyParallel` / `ParallelToDimensionLine`) are retained only for deprecated/optional cross-cutting collectors and must not gate the wall-axis main flow. Ordering, source-aware dedupe, diagnostics, summaries, and the `QuickDimensionReadOnlyResult` contract shape are retained. Phase 1 spike services/models/commands are untouched.
Scope guard: MVP supports active Plan Views and straight non-curtain host walls only. Arc/non-line host walls, curtain walls, linked models, columns, grids, and non-selected walls are out of scope for the wall-axis main flow.

### ADR-2026-07-12: Wall-end anchor = physical solid caps by min/max projected station
Status: ACCEPTED and implemented as part of the Phase 2.6 smoke-fix loop on 2026-07-12.
Decision: Wall-end anchors are the two wall-direction-aligned `PlanarFace` references whose centroids project to the minimum and maximum stations on the selected wall axis. These min/max faces are the physical wall solid end caps used for drafting-visible wall-corner anchoring. `QuickDimensionOptions.WallEndStationTolerance` remains only as a degeneracy guard when min/max stations are not distinct.
Rationale: Wall `LocationCurve` endpoints can lie on the centerlines of joining walls, not at the visible wall-corner/intersection. In a 200 mm butt-join, the physical start cap may be offset about 100 mm from station 0. The earlier "face must be near station 0 or Length" rule rejected the real cap and left the first opening jamb as the first candidate. Opening reveal/jamb faces share the wall-axis normal but sit between the two physical solid caps, so min/max projected station separates solid ends from openings without anchoring to centerline endpoints.
Implementation: `QuickDimensionWallCandidateCollector.GetBestWallEndFaceCandidates` collects all wall-direction-aligned planar face candidates with `Options.ComputeReferences = true`, computes station directly via `QuickDimensionLineContext.ProjectParameter`, then selects `OrderBy(ParameterOnDimensionLine).First()` and `OrderByDescending(ParameterOnDimensionLine).First()`. `CollectWallEndFaceCandidates` does not call `TryProjectPointToPickedSpan`, so physical caps slightly outside the LocationCurve span due to joins are not silently dropped.
Consequences: Wall-end anchors now match the physical wall corner/intersection seen by the user instead of the LocationCurve centerline endpoint. Opening jamb faces are not used as wall anchors because they are interior to the min/max caps. This rule is scoped to straight non-curtain walls in MVP; arc, stacked, curtain, or heavily modified wall geometry still requires explicit future validation.

### ADR-2026-07-12: Chain-dimension readiness requires distinct projected stations
Status: ACCEPTED and implemented as part of the Phase 2.6 smoke-fix on 2026-07-12.
Decision: `QuickDimensionReadOnlyResult.CanCreateChainDimension` is true only when there are at least two final candidates AND every final candidate sits at a distinct projected station within `QuickDimensionOptions.DuplicateTolerance`. `QuickDimensionReadOnlyEngine` performs a global projected-station dedupe after source-aware dedupe; each removed collision emits a `QuickDimensionRejectedReason.DuplicateStation` diagnostic that names the kept candidate.
Rationale: Chain dimensions cannot use zero-length segments. Two candidates at the same projected station (for example a wall-end face collision with an opening jamb, or two touching openings sharing a jamb station) would either produce zero-length dimension segments or Revit-side rejection when handed to `NewDimension` in Phase 3. Reporting readiness only when stations are distinct is safer than trusting `CandidateCount >= 2` alone.
Implementation: `QuickDimensionReadOnlyEngine.RemoveDuplicateStations` runs after `QuickDimensionGeometryService.DeduplicateCandidates`. It sorts candidates by station, keeps the first candidate at each station, and emits a diagnostic for any dropped collision. `QuickDimensionReadOnlyResult.CanCreateChainDimension` uses a private `CountDistinctStations` helper backed by `DuplicateTolerance`.
Consequences: Read-only summary now reports chain readiness accurately, so future Phase 3 code can rely on `CanCreateChainDimension` as a real precondition. Diagnostics preserve the full audit trail for collision cases, keeping the "explain what was ignored" invariant.

### ADR-2026-07-12: Read-only summary uses millimeters for user-visible values
Status: ACCEPTED and implemented as part of the Phase 2.6 smoke-fix on 2026-07-12.
Decision: Any user-visible measurement rendered by `QuickDimensionReadOnlySummaryCommand` (wall-axis length and each ordered candidate's `t`) is converted to millimeters via `UnitUtils.ConvertFromInternalUnits(value, UnitTypeId.Millimeters)`. Diagnostics that surface station or tolerance values in the dialog (missing wall-end faces, duplicate station collisions) also emit millimeters.
Rationale: The user works in millimeters. The initial smoke output printed values in Revit internal feet, which made the smoke report unreadable and blocked verification of correctness at a glance.
Implementation: Storage and internal math remain in Revit internal feet; only presentation-layer strings are converted. Internal APIs (`ProjectParameter`, `Length`, `WallEndStationTolerance`, `DuplicateTolerance`) continue to accept and return internal feet.
Consequences: Presentation and math stay separated. Any new user-facing text in Quick Dimension must call `UnitUtils.ConvertFromInternalUnits(..., UnitTypeId.Millimeters)` before formatting.

### ADR-2026-07-17B: Wall Spike side-face directional full-height resolver
Status: ACCEPTED FOR ISOLATED WALL SPIKE after Revit 2026 smoke PASS on 2026-07-17. Do not claim production Quick Dimension is updated until this resolver is ported to `QuickDimensionWallCandidateCollector.CollectSelectedWallEndAnchors` and smoked there.
Context: Prior Wall Spike models failed across L/T joint cases: top-face/intersection and join-role heuristics were rejected; vertical-only side-face edges passed T-joints but failed L-joints; simple joined-wall outward extension fixed some exterior cut corners but overshot interior corners or fell back to raw side-run endpoints. XML logs showed correct anchors depend on shell and end direction, not a single min/max or always-outward rule.
Decision: Keep the selected-wall side-face boundary model. Collect vertical side-face edge midpoints (`Reference != null`) and horizontal side-run endpoints. Choose the longest horizontal side-run endpoints as base anchors. Resolve each end directionally: for `Interior`, choose the nearest full-height vertical reference in the inward direction into the selected wall span from selected+joined side-line candidates; for `Exterior`, choose an outward joined full-height vertical reference when one exists on the side line, otherwise keep the selected-wall base. `CollectJoinedWallBoundaryCandidates` remains limited to candidates within `DistanceToSideLine <= 5mm` and `JoinExtensionMargin=500mm`.
Critical invariant: Full-height filtering must compute `maxMidpointZ` only from candidates with `Reference != null` and `Point != null`; horizontal endpoints at top elevation must never define the full-height threshold.
Evidence: User smoke on 2026-07-17 passed 12/12 Left/Right cases for walls 379467, 379468, 379469, 379470, 379933, and 380187. XML diagnostics recorded expected survey N/E anchors for selected wall cutting others, selected wall being cut, and T-joint cases.
Next step: Prove one-axis mixed L/T station aggregation for one selected wall through research and self-critique before porting the resolver or creating dimensions.

### ADR-2026-07-17C: Quick Dimension remains one selected-wall chain at a time
Status: ACCEPTED.
Context: A production plan contains mixed L-joint and T-joint conditions. The Wall Spike 100% smoke pass proves individual left/right end-anchor extraction only; it does not prove that mixed joint stations form a correct continuous dimension chain. Bulk creation across many walls would prevent reliable operator validation of geometry-dependent output.
Decision: The main flow accepts exactly one straight, non-curtain host Wall and one side pick per invocation. It may create only one dimension chain on that wall axis. The chain contract must aggregate relevant L-joint/T-joint stations and later hosted opening jamb stations in ascending axis order, with explicit duplicate-station diagnostics. The resolver must be researched and self-criticized against mixed L-L, T-T, L-T, T-L, reversed-axis, and coincident-station counterexamples before any production code is written or ported.
Consequences: No automatic or multi-wall batch dimension creation. Per-joint anchor correctness is a required input invariant, not chain-level acceptance evidence. The Wall Spike remains open until aggregation is isolated, diagnosable, Revit-smoked, and only then integrated with the production collector.

### ADR-2026-07-18A: Mid-run wall-joint station detection uses side-line reference evidence with endpoint-join exclusion
Status: ACCEPTED FOR RESEARCH/LOG-ONLY CONTRACT after Section 11 smoke PASS on selected wall 380815; REFINED on 2026-07-19 after four additional real smoke audits. Do not treat this as production collector implementation until the side-face end-anchor resolver is ported and the reference-preserving read-only wall-joint aggregator is implemented/smoked separately.
Context: Session 2.7 Section 11 smoke used a mixed fixture with one selected straight wall, two end joins, one oblique mid-run T-wall (381185), and a nearby parallel non-join wall (381035). `LocationCurve.get_ElementsAtJoin(0/1)` reported only the two selected-wall ends; `JoinGeometryUtils.GetJoinedElements` returned no mid-run wall. The mid-run T-wall was oblique, so a perpendicularity gate rejected a real station. A first log version collapsed two T-joint jambs into one midspan-best representative. Four follow-up smoke sets on 2026-07-19 then showed endpoint join walls can expose raw vertical side-line references and be overcounted if raw reference evidence is accepted before endpoint join provenance.
Decision: Raw mid-run evidence is a vertical `Edge.Reference` on the selected side line whose adjacent face normal is along the selected wall axis. Accepted mid-run classification must additionally exclude candidate walls in `ElementsAtJoinStart` or `ElementsAtJoinEnd`, reject endpoint-zone and resolved-anchor duplicate stations, sort/dedupe accepted stations, and require at least two distinct accepted stations (`acceptedMidRunStationCount >= 2`) before classifying a candidate wall as `MidRunCrossing`. Join API membership and perpendicularity remain diagnostics/provenance; join membership is an exclusion for true mid-run acceptance, not a positive mid-run signal. Reference ownership for the tested mid-run T-joint lives on the joining wall, not the selected wall.
Evidence: Right/Interior smoke on wall 380815 logged wall 381185 as `MidRunCrossing` with two `ReferenceHit` stations: 2665.787mm and 2867.289mm, both `candidateReferenceNormalAlongAxis=true`; all join provenance flags were false and `isPerpendicular=false`. Left/Exterior logged no mid-run hits for 381185, proving shell-specific behavior. Parallel near wall 381035 stayed `ParallelNonJoined`. 2026-07-19 audits found false `MidRunCrossing` records for end-join walls such as 380858, 379470, 379468, 379467, and 379469; each is now expected to remain `EndJoinOnly` even if raw `referenceHitCount > 0`.
Consequences: Future read-only wall-joint aggregation must assemble resolved Start/Finish anchors from ADR-2026-07-17B plus only accepted side-line reference hits from non-end-join candidate walls inside the resolved anchor span, ordered by projected station. It must dedupe coincident anchor/joint hits, preserve near-distinct jamb stations, reject endpoint artifacts, retain live `Reference` values for production, and still precede any `ReferenceArray`/`NewDimension` work.

### ADR-2026-07-19A: Accepted mid-run stations exclude endpoint join artifacts
Status: ACCEPTED FOR LOG-ONLY CLASSIFIER AND FUTURE PRODUCTION AGGREGATION GATE. Follow-up Revit re-smoke on 2026-07-20 passed across four real Wall Spike sets; production collector + read-only aggregator port may proceed. `NewDimension` work remains blocked until reference-preserving read-only aggregation passes.
Context: Four real Wall Spike smoke audits showed that raw vertical side-line `Edge.Reference` evidence alone overcounts endpoint joins. Walls in `ElementsAtJoinStart` or `ElementsAtJoinEnd` can expose side-line reference hits at or near the selected wall endpoint/anchor zones; those hits were incorrectly classified as `MidRunCrossing` even though they are end-join artifacts. Some artifacts do not exactly equal the resolved Start/Finish anchor station, so anchor-station duplicate filtering alone is insufficient.
Decision: Treat `ElementsAtJoinStart` and `ElementsAtJoinEnd` as exclusion provenance for true mid-run acceptance. A true mid-run candidate must: expose vertical `Edge.Reference` hits on the selected side line; have `candidateReferenceNormalAlongAxis=true`; not belong to either selected-wall end join set; produce at least two distinct accepted stations after filtering; keep stations strictly inside the resolved Start/Finish anchor span; drop hits near resolved Start/Finish anchors and raw location-curve endpoint zones (`0`/`axisLength`); sort and dedupe by station tolerance. Raw `ReferenceHits` remain diagnostic evidence only; `acceptedMidRunStationCount` is the gate for `MidRunCrossing`.
Consequences: `QuickDimensionWallMidRunProbeService` receives `QuickDimensionWallSpikeResult`, separates raw hits from accepted station count, makes `EndJoinOnly` win before `MidRunCrossing`, and requires `acceptedMidRunStationCount >= 2`. `QuickDimensionWallSpikeXmlLogService` emits `acceptedMidRunStationCount` per candidate. Production aggregation must use the same acceptance rule while preserving live Revit `Reference` objects; the current probe remains value-only/log-only and must not be directly promoted into `ReferenceArray` creation. Re-smoke evidence: 380815→381185, 379467→379933, 379469→379933, and 379470→380187 were accepted only on the true mid-run shell; opposite shells and endpoint joins stayed clean.

### ADR-2026-08-04A: Multi-agent work package as the default workflow for context-heavy ArcTool work
Status: ACCEPTED.
Context: Multi-file bug fixing, cross-file logic tracing, runtime-evidence review, and roadmap-scale implementation can overflow one long chat and make resume/handoff brittle. The proven Quick Dimension package showed that one master orchestrator plus many narrow workers, each with explicit write scope and compact result envelopes, scales better than ad-hoc broad prompts.
Decision: For ArcTool tasks that touch 3 or more source files, require runtime/smoke evidence, or are roadmap phases, architecture audits, or regression matrices, the default execution model is a work package built from `.claude/workpackages/_TEMPLATE/` and invoked through `.claude/skills/arctool-work-package/SKILL.md`. Standing authorization is granted to spawn Agent-tool subagents inside this workflow without per-dispatch confirmation. One worker owns exactly one task file, reads only the shared contract + that task file + the minimum evidence excerpt, and returns only the compact schema envelope; the master alone updates evidence queue and execution state. Revit runtime remains operator-controlled. Gemma 4 stays limited to code-generation tasks inside the package; Claude remains responsible for investigation, architecture, review, evidence interpretation, build verification, and orchestration.
Consequences: Context-heavy work becomes resumable, auditable, and safer through write-lock serialization and uniform envelopes, while small/local tasks stay direct to avoid scaffold overhead. The live Quick Dimension package remains at `.claude/quick-dimension-bugfix/` and is not relocated while its historical results and handoff paths are still active.

### ADR-2026-08-04B: Post-transaction rollback validation is a separate track from candidate/audit correctness
Status: ACCEPTED.
Context: The Quick Dimension BUG-11/BUG-10 mission fixed candidate reference-station atomicity and fallback candidate metadata in `QuickDimensionDoorWindowCandidateCollector.cs`, plus audit logging in `QuickDimensionReadOnlyXmlLogService.cs`. Its shared contract originally also required forced-rollback evidence. Analysis showed every operator-reachable invalid input returns `Result.Cancelled` before `Transaction.Start()`, so the rollback branches in `QuickDimensionChainCreationService` execute only on internal post-start failures (`NewDimension` returns null, reference-count mismatch, non-`Committed` status, thrown exception). The operator cannot manufacture such a failure through normal modelling, so the gate was unsatisfiable as a plain smoke request and blocked closure of otherwise-verified fixes.
Decision: Forced-rollback validation is a standalone verification track, not an acceptance gate for collector, candidate-metadata, or audit-logging changes. A mission may close on creation correctness plus reopen persistence when no task in that mission holds `QuickDimensionChainCreationService.cs` in its write scope, because rollback behavior is then byte-identical to the pre-change build and is not a regression surface. Rollback must be validated through a fault-injection harness or debug-only switch that forces a post-`Transaction.Start()` failure without altering the production creation path; it must never be requested as an operator smoke. The deferred track is recorded in `.Dossier/Quick Dimension - Deferred Rollback Validation Task.md`, and closing evidence for it is a clean rollback with no dirty transaction, the original read-only XML preserved, and no orphan `Dimension`.
Consequences: Verified fixes close on their own evidence instead of stalling behind an unreachable gate, and the deferral stays honest because the untested behavior is explicitly tracked rather than dropped. The trade-off is that Phase 3's "failure leaves no dirty transaction state" criterion remains runtime-unproven until that separate track runs. Any future mission that does edit `QuickDimensionChainCreationService.cs` must reinstate rollback validation as an in-scope gate.

## PATTERNS
Use domain-prefixed enums for new models. Keep QD options and results immutable or near-immutable. Keep source-aware diagnostics for both accepted and rejected elements. Centralize axis normalization in `QuickDimensionLineContext` so collectors do not duplicate direction/span/projection math. For the wall-axis projection model, the participation test is point projection onto the selected wall axis (`ProjectParameter` within `[0, Length]`) for openings, while wall-end anchors use min/max projected station among physical solid-cap candidates and are not forced to match LocationCurve endpoint stations. Door/Window openings hosted in the selected wall must contribute BOTH left and right jamb references projected onto the wall axis; build opening jamb points along the WALL direction. Dedupe must remain source-aware and conservative so Door/Window left/right references on the same instance are preserved. Wall-end anchors use geometry-derived planar face references (`WallEndFace`) from min/max projected station, while legacy side-face wall references (`WallSideFace`) remain tied to the optional cross-cutting path. Chain-dimension readiness must never be inferred from raw candidate count alone; enforce distinct projected stations before declaring readiness. User-facing values render in millimeters via `UnitUtils.ConvertFromInternalUnits` while internal math stays in Revit internal feet.

## TRADEOFFS
The contracts intentionally reference Revit API value/reference types rather than pure DTOs because Phase 3 needs stable `Reference` objects for `ReferenceArray`. This keeps the read-only engine Revit-aware but avoids holding mutable `Element` objects or modifying documents. The geometry service is deliberately document-free, so collectors remain responsible for API access, unsupported-case diagnostics, and source-specific reference extraction. The wall-axis projection model trades generality (any drawn line across many elements) for correctness and predictability (one selected wall, its openings, its end anchors) — this matches the real drafting intent and removes whole classes of false rejections. Wall-end anchors use geometry inspection because the Revit 2026 host-object utility surface does not provide end-face extraction. The min/max cap rule intentionally trusts the straight non-curtain wall solid topology: openings are interior cuts, physical end caps are extrema. The deprecated intersection helpers stay in the codebase as dead-but-tested utilities until the optional cross-cutting/grid path is either revived or removed. Chain-dimension readiness enforcement adds one extra pass over final candidates, which is negligible for MVP scope and eliminates a whole class of Phase 3 failure modes.

## PHILOSOPHY
Reference correctness and explainable diagnostics come before UI polish. Unsupported geometry should produce explicit diagnostics instead of silent omission or speculative heuristics. Choose the geometric model that matches the user's drafting intent (measure along a wall) over a more general model that produces structurally wrong candidate sets. Match units and vocabulary to the user's day-to-day workflow when presenting results.
