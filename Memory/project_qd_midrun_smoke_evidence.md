Session 2.7 Section 11 log-only smoke ran on 2026-07-17 on selected wall 380815 (Generic 200mm), fixture with two end joints plus one oblique mid-run T-joint. **RESULT: the experiment succeeded and confirms the research gap. Wall Spike stays OPEN.**

**Confirmed root cause — join APIs are blind to mid-run T-joints:**
- Right/Interior log: `ElementsAtJoinStart={380916,380815}`, `ElementsAtJoinEnd={380815,380858}`, `GeometryJoin count=0`. The mid-run T-wall 381185 has `inElementsAtJoinStart=false, inElementsAtJoinEnd=false, inGeometryJoin=false`.
- This empirically proves `LocationCurve.get_ElementsAtJoin(0/1)` only reports the two curve ENDS, and `JoinGeometryUtils.GetJoinedElements` returned nothing for this fixture. No join API discovered the mid-run T-joint. The classifier's `inAnyJoin` requirement is therefore a WRONG signal for mid-run detection.

**Second wrong signal — perpendicularity:** the mid-run T-joint is oblique, so 381185 has `isPerpendicular=false`. The `isPerpendicular` gate also rejects a real mid-run station. Do not require perpendicular.

**The CORRECT detection signal (present in the data, independent of joins):** wall 381185 has `candidateWallExposesRefAtStation=true`, `candidateReferenceNormalAlongAxis=true`, `distanceToSideLineMm=0`, `stationMm=2665.787` (strictly inside span 57.7..4995.8). So a mid-run station is identified by: a vertical `Edge.Reference` ON the selected side line (distance≈0) with normal along the selected axis, at a station strictly inside the span. NOT join-set membership, NOT perpendicularity. The current classifier mislabeled 381185 as `NonJoinedProximity` and reported `mid-run crossings: 0` purely because of the two wrong gates.

**Decisive answer on reference ownership:** at the mid-run T-joint, `selectedWallExposesRefAtStation=false` while `candidateWallExposesRefAtStation=true`. The selected wall exposes only a `horizontal-endpoint` at that station (no vertical reference); the usable Reference must come from the JOINING wall (381185), not the selected wall. This resolves research question 5/7: mid-run dimension references are owned by the joining wall.

**Two jambs, ~one wall thickness apart — and the log collapses them to ONE (probe defect found 2026-07-17):** the mid-run T-joint has TWO jamb stations — 2665.787mm (n=20417.016/e=20116.839) and 2867.289mm (n=20502.175/e=20299.461), ~202mm apart ≈ 200mm wall width. The probe logged ONLY 2665.787 as the candidate reference; 2867.289 survives only as a selected-wall `horizontal-endpoint` corner with no reference. Root cause: `QuickDimensionWallMidRunProbeService.TryFindVerticalReferenceOnSideLine` collects all side-line hits but returns a SINGLE representative via `OrderBy(distance).ThenBy(|station - midspan|)`. axisLength=5060.757 → midspan=2530; 2665.787 (Δ135) beat 2867.289 (Δ337), so the far jamb was dropped. This is a real log-layer limitation: a mid-run T-joint contributes TWO stations and the current log hides one. FIX before re-smoke: log ALL vertical-reference hits on the side line strictly inside the span (a list per candidate wall), not one representative. Note the user initially mis-read candidate 18 (wall 380858, the finish END-join wall at 21401.729/22228.562 = Finish Anchor, correct) as the mid-run point; the actual mid-run reference is candidate 21 (wall 381185).

**Shell-specific, not symmetric:** in Left/Exterior the same wall 381185 is `Ignored`, `distanceToSideLine=100mm`, `candidateWallExposesRefAtStation=false`. The mid-run station only exists on the shell the joining wall butts into (Interior here). This falsifies the "reversed side pick is symmetric" assumption — mid-run detection is shell-specific.

**False-positive guard works:** parallel near wall 381035 (distanceToSideLine≈205/405mm) is correctly `ParallelNonJoined`, not a station. The nonjoined-proximity guard held.

- **Confirmed defect (BUG-09, 4/4 reproducible): anchor `FinalCandidate.elementId` is hardcoded to the selected wall id.** In `QuickDimensionWallCandidateCollector.TryCollectWallEndAnchors` the Start/Finish anchor `QuickDimensionCandidate` are constructed with `wall.Id` (selected wall) as the first `elementId` arg, while the resolved reference and its true owner live on `spikeResult.StartAnchor.EdgeReference` / `FinishAnchor.EdgeReference` (owner = `EdgeReference.ElementId`). `ReadOnlyResult.StartAnchor/FinishAnchor.elementId` already record the correct owner, so the value exists but is not propagated to the final candidate.
- **Mechanism explains all 4 results:** when an anchor snaps INWARD (Interior shell) it resolves onto the selected wall's own reference, so hardcoded `wall.Id` accidentally matches — appears correct. When an anchor extends OUTWARD (Exterior shell) it resolves onto a JOINING wall's reference (e.g. test1 Right Finish→380858; test4 Left Start→379469, Left Finish→379467), so `FinalCandidate.elementId` mismatches the `stableReference` owner. The bug only surfaces on extends-outward anchors; every Exterior/Left anchor in tests 1–4 shows the mismatch.
- **Impact:** if `NewDimension` uses only the live `Reference`, dimensions still create. But any pre-`NewDimension` guard that verifies `FinalCandidate.elementId` owns its `stableReference` will falsely fail on join-corner anchors. Fix is metadata/contract only, no classifier change: at anchor construction pass the reference owner id (`spikeResult.StartAnchor.EdgeReference.ElementId`) instead of `wall.Id`. Fix before porting `NewDimension`.
